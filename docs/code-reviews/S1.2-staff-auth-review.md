### Hunt list (tailored to the diff; corrected 2026-10-13 — items 1, 2, 3, 6, 7, 10, 11 and 12 first asked for things the code does not do, or left out what the VS Code leg added)

1. The guard's decision is the only gate and it is complete: every file under `src/app/admin/` that renders protected content or mutates takes it before any read or write — `guardAdminPage` in the three content pages; `getStaffAccess` (the same `decideAccess`) in the sign-in, verification and enrolment pages and in `verifyTotp`, `startEnrolment` and `confirmEnrolment`, which act on the decisions that are not `allowed`; `guardAction` is the wrapper for later actions and has no caller at S1.2. The two stated exceptions: `signIn` runs before a session exists (the throttle, then the Auth server, then the decision) and writes one audit row for a refused password with the privileged client before any session; `signOut` only ends the caller's own session and deletes that session's cookies whatever the Auth server answered or threw (`forgetStaffSessionCookies` — the library keeps them when the session's token has expired and the Auth server cannot be reached). No page or action trusts a cookie's decoded content, a layout's result, a hidden field, a query value or a client-held role; `src/proxy.ts` makes no access decision and cannot be relied on for one (it refreshes cookies on `/admin/:path*` only, and a cookie that makes the library throw does not fail the request).
2. MFA cannot be skipped: no route or action accepts `aal1` as a staff session; the enrolment page needs a password session of a staff account and nothing else — first enrolment is trust on first use, stated as a residual risk in `docs/THREAT-MODEL.md` §5; a verified factor is required before `/admin` renders. The assurance level is the `aal` claim of the session's access token, decoded locally by auth-js — trusted only because `auth.getUser()` has had the Auth server validate that very token earlier in the same call (the order is pinned by a unit test); no level is taken from a token the Auth server has not vouched for.
3. The decision table is implemented as recorded and in the recorded order (unavailable → login with `next` → not_staff → revoked → enrol → verify → forbidden → allowed): an account without a staff row, or a revoked member, can never reach the verification or enrolment step; no profile → the honest notice with a sign-out control on a page render, and the sign-in actions end the session themselves (a Server Component cannot clear cookies — a recorded departure from the prompt's "signed out locally"); inactive or revoked → the revoked state; missing area → "Access restricted" with nothing read; configuration failure, an Auth server that cannot be reached or does not answer as itself, a database failure or a library call that throws → unavailable, never a pass and never "no user". `decideAccess` is pure and unit-tested row by row and for the order.
4. Authorisation mirrors the architecture: the role → areas map in `src/lib/staff/permissions.ts` equals the SQL function's body; the route → areas map gives `/admin/staff` → `settings`, `/admin/support` → `support`, `view=refunds` → `support` + `finance`; Operations is denied `settings` and `finance`, Customer support `settings`, `finance` and `catalogue`; a denied page writes nothing and leaks no record; a path the table does not know is given the owner-only requirement by its page.
5. 0003_staff_auth: additive; the one policy is non-recursive (own row at `aal2`, both Auth helpers in scalar sub-selects) and the grant is SELECT only; the function is immutable, pinned, EXECUTE revoked from `public` and `anon`; no `SECURITY DEFINER`; TRUNCATE stays revoked; the down file reverses exactly — no cascade — and states its data loss; the baseline-inventory test lists four migrations; the change record matches the SQL, its verification texts are what Postgres prints, and its P8 comparison is by column position with the policies hashed.
6. Fail closed: the throttle refuses on a missing name, a network error, a timeout or an unexpected response, in both steps — the password step counts the address (one normalised spelling) and the client address before the password is checked; the code step counts each six-digit code against the member before the Auth server sees it; the limits are as recorded (5 / 20 / 5 per 15 minutes); no e-mail address, client address or user id reaches Redis or a log in clear (SHA-256 only, unsalted).
7. Secrets and PII: no TOTP secret, QR, token, password or address is logged, written to a record or returned in an error body; the QR and the key go to the member's browser once and are never sent back (the confirm step posts the factor's id, checked as a UUID, and the code); a refused password's audit row carries the e-mail hash only; a failed audit write logs the action and an error code and nothing else; `.auth/` is git-ignored and a failed Playwright test writes no page snapshot while a key is on screen; no live value anywhere in the range (the full-history secret scan is clean on the rewritten branch).
8. Redirect safety: `safeNextPath` accepts only a same-origin path under `/admin` (no scheme, host, `//`, backslash, control character; decoded once and re-checked), refuses the sign-in pages with or without a query, and falls back to `/admin`; the sign-in, verify and enrol pages use it for every redirect.
9. Boundary: `@supabase/ssr` and the server modules are imported by server code only; `src/lib/server/staff-session.ts` may import `@supabase/ssr` and SDK types and nothing else of the SDK; the "use client" enrolment form — the only client module under `/admin` — imports the two actions, never a server module or the SDK; the Upstash names are read inside `src/lib/server/` only; the import-boundary tests prove it; the CSP changes by `data:` on `img-src` alone and the enrolment QR is rendered through `<img src="data:…">`, never inline HTML.
10. Revocation and recovery: `revokeStaffAccess` reads the row, sets `active = false`, `revoked_at`, `revoked_reason`, bans the Auth user and writes the audit row — written once the row has changed, whatever the ban answered, and recording the state that was read; the guard reads the row on every request so the next request is denied; revocation does not delete the member's sessions, and what a lifted revocation or a factor reset leaves usable is stated in `docs/THREAT-MODEL.md` §5; the recovery route is documented and was exercised on TEST (the VS Code leg's evidence). The function has no caller before S2.1; it is unit-tested against a recording client and the TEST tool performs the same writes.
11. The TEST tool and the harness: `pnpm db:test:staff-users` is dry-run by default (every write in its code comes after the dry-run return), TEST-only through the existing target guard, creates users only from the `E2E_STAFF_*` names (whole `@example.test` addresses), prints no password or secret, and `--revoke` / `--restore` / `--reset-mfa` touch only the three named users — never a row that differs from the fixture or holds the owner role, never twice — with an audit row that states the previous state as read; the auth-setup project keeps the TOTP secret under `.auth/` and never prints it; the sign-out test runs once, after both required projects, and proves the session is ended on the server; the required-projects gate is unchanged.
12. Copy: the labels the final Admin contains are quoted exactly; every other string is an NS row under D-24 whose approval is recorded with its evidence (`docs/content/new-strings.md` §4, 2026-10-13); nothing from the prototype's sign-in preview is ported (D-32e).
