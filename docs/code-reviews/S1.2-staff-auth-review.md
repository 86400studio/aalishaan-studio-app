### Hunt list (tailored to the diff; scale at handoff to what the VS Code leg adds)

1. The guard is the only gate and it is complete: every file under `src/app/admin/` that renders protected content or mutates calls `guardAdminPage` / `guardAction` before any read or write; no page or action trusts a cookie's decoded content, a layout's result, a hidden field, a query value or a client-held role; `src/proxy.ts` makes no access decision and cannot be relied on for one (it refreshes cookies on `/admin/:path*` only).
2. MFA cannot be skipped: no route or action accepts `aal1` as a staff session; the enrolment page needs a password session of a staff account and nothing else; a verified factor is required before `/admin` renders; `getAuthenticatorAssuranceLevel()` is read from the Auth server, never inferred.
3. The decision table is implemented as recorded (unauthenticated → login with `next`; `aal1` + factor → verify; `aal1` without → enrol; no profile → signed out locally with the honest notice; inactive/revoked → the revoked state; missing area → "Access restricted" with nothing read; configuration or Auth failure → unavailable, never a pass) and `decideAccess` is pure and unit-tested row by row.
4. Authorisation mirrors the architecture: the role → areas map in `src/lib/staff/permissions.ts` equals the SQL function's body; the route → areas map gives `/admin/staff` → `settings`, `/admin/support` → `support`, `view=refunds` → `support` + `finance`; Operations is denied `settings` and `finance`, Customer support `settings`, `finance` and `catalogue`; a denied page writes nothing and leaks no record.
5. 0003_staff_auth: additive; the one policy is non-recursive (own row at `aal2`) and the grant is SELECT only; the function is immutable, pinned, EXECUTE revoked from `public` and `anon`; no `SECURITY DEFINER`; TRUNCATE stays revoked; the down file reverses exactly and states its data loss; the baseline-inventory test lists four migrations; the change record matches the SQL.
6. Fail closed: the throttle refuses on a missing name, a network error, a timeout or an unexpected response; it counts both keys before the password is checked; the limits are as recorded; no e-mail address or client address reaches Redis or a log in clear (SHA-256 only).
7. Secrets and PII: no TOTP secret, QR, token, password or address is logged, written to a record, returned in an error body or stored outside the user's own browser response; the audit rows carry the e-mail hash only for failed sign-ins; `.auth/` is git-ignored; no live value anywhere in the range.
8. Redirect safety: `safeNextPath` accepts only a same-origin path under `/admin` (no scheme, host, `//`, backslash, control character; decoded once and re-checked) and falls back to `/admin`; the sign-in, verify and enrol pages use it for every redirect.
9. Boundary: `@supabase/ssr` and the server modules are imported by server code only; the "use client" enrolment form imports actions, never a server module or the SDK; the Upstash names are read inside `src/lib/server/` only; the import-boundary tests prove it; the CSP changes by `data:` on `img-src` alone and the enrolment QR is rendered through `<img src="data:…">`, never inline HTML.
10. Revocation and recovery: `revokeStaffAccess` sets `active = false`, `revoked_at`, `revoked_reason`, bans the Auth user and writes the audit row in that order; the guard reads `active` on every request so the next request is denied; the recovery route is documented and was exercised on TEST (the VS Code leg's evidence).
11. The TEST tool and the harness: `pnpm db:test:staff-users` is dry-run by default, TEST-only through the existing target guard, creates users only from the `E2E_STAFF_*` names, prints no password or secret, and `--revoke` / `--restore` / `--reset-mfa` touch only the three named users; the auth-setup project keeps the TOTP secret under `.auth/` and never prints it; the required-projects gate is unchanged.
12. Copy: the labels the final Admin contains are quoted exactly; every other string is an NS row under D-24 with its approval state recorded; nothing from the prototype's sign-in preview is ported (D-32e).
13. Records: the trackers, the change record, THREAT-MODEL and the sprint record state nothing as applied, tested or reviewed that has not happened; the Node 22 difference is recorded beside every cloud check (D-43); the flagged deviations are stated plainly.
