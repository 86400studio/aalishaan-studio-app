## What and why

The independent review of the S1.7 candidate at `9b673ec` (round 4, 2026-11-28) returned two Blocking findings. Both lie inside functions that `0007` and `0008` define — applied on TEST, so not editable — and both are of one kind: the durable result depended on which writer took the order's lock first, though the same evidence reached the database. Only rules under the database's own row locks (the checkout row, then the order, then the payment) can close them:

- **Finding 1 — a signed authorisation could hide a matching API observation.** 0008's failure rule (its contract 1, with 0007's) recognises a conflict by the provider check's hold record — an audit row `payment.hold.*` with reason `provider_check` naming the payment. When A's signed `payment.authorized` took the order's lock first, it raised the `authorized_only` hold itself (reason `authorized_event`); an already-running provider check that then observed A authorised found the hold standing, raised nothing and recorded nothing (0007's step: an equal or stronger hold stands). A's signed `payment.failed` then found no provider-check record — `stale_failed` — and A's timely signed capture confirmed the order, advanced its item and queued `send_confirmation`; with the check first, the same evidence kept the order under review at stage 0 with no task. Now the check keeps its observation of that payment once even over a hold that already stands — as the record a hold it raised would be — and the failure rule reads it in both lock orders.
- **Finding 2 — a signed failure could suppress the first verified Checkout return for an extra payment.** 0008's `payment_return_state` decided whether it had already recorded a verified return by the payment row's `signature_verified` — which a signed event sets too. When B's signed failure created B's row (`failed`, verified), A's capture then confirmed the order and B's first valid Checkout return arrived, the return recorded nothing: no `payment.return.verified` row, no discrepancy flag — if B's next webhook were delayed or lost, staff would see a confirmed order with no sign that B needs reconciliation. Now a return is recorded once per payment by its own `payment.return.verified` row, and judged; B keeps its failed status.

The same "which writer came first" analysis, run by the builder over every arrival order of the evidence these rules read (the harness's arrival-order engine — "What has been checked so far") and by the adversarial review of the fix (the S1.7 record → H.18), found the findings' neighbours under 0008, closed here with them:

- **Finding 1 from the other side.** A's signed failure taking the lock before an already-running check — the failure `stale_failed` beside the signed authorisation, or `recorded:failed` with money no payment row can hold (so no row was written) — let the check raise or keep the hold, and A's timely capture confirmed; the check first, the same evidence was the review. Now a processed signed failure of a listed payment in the ledger, for the checkout's own provider order, is the review, as a failed row already is (0007), for an order that could be held. Of the six arrival orders of A's signed authorisation, the check and A's signed failure, three confirmed under 0008 and three were the review; under 0009 all six are the review.
- **Finding 2 before the confirmation.** B's signed failure and B's verified return both before A's capture: under 0008 the return recorded nothing (finding 2's cause) or, with the return first, B's later failure made B "not live" — so A's capture confirmed and nothing flagged B, while with A's capture first B's return flagged the confirmed order only when it came before B's failure (after the failure, that was finding 2 itself: nothing). Now the report and the signed failure of one payment are a contradiction a person resolves: whichever of the two arrives second flags the order (`payment_state_conflict`), so A's later capture is never the confirmation that leaves B unflagged — and the order is never left payable, its checkout inviting a second payment, beside the contradiction. The same holds for the order's own payment A: its verified return and its signed failure are the review, a signed authorisation of A between them included.

Not in this file: any change to `payment_record_event`, `protect_provider_event` or `order_confirmation_view`; any table, index, grant or policy; the checkout page or any server code; a refund, a cancellation, a staff surface for reviews or any scheduled work.

**What 0009 amends.** The 0008 record's contracts 1 (its failure rule — the repeated-or-older branch's — now also reads the record the check keeps over a standing hold, and also meets a payment a verified return reported), 2 (the forward branch's failure rule, 0007's, meets that payment too), 3–5 (a return recorded once per payment by its own row; the confirming payment's own first return now writes that row, no review; its audit rows carry the payment row's status; a return of a payment whose signed failure was recorded is the conflict); the 0007 record's contracts 1 (the failure rule — and the verified return beside it), 5 (the hold — now also the observation over a standing hold, and a signed failure in the ledger stops it), 6 (`payment_state_conflict` — now also a processed signed failure in the ledger) and 9 (an exact repeat writes nothing — the first observation over a standing hold now writes one row); the 0006 record's contracts 5 (a repeated or older failure of a payment a verified return reported is the conflict too, for an order that could be held), 8 and 9 and the 0005 record's contracts 8 (the same), 9, 10 and 11, through those. ## Security check

- **Privileges.** No function is `SECURITY DEFINER`; each has `set search_path = ''` and schema-qualified names. They run as `service_role` with the table privileges 0002 already granted it. The publishable key (`anon`) and a signed-in staff member (`authenticated`) cannot execute any of them (42501), and no table grant or policy changed: the browser still reaches no order, payment or event data.
- **No generic entry point.** No dynamic SQL, no statement assembled from an argument; the arguments are validated by 0005's and 0006's patterns before use, and the new steps compare and store values only. The ledger read compares the payment entity's id and provider order id as text — values 0005's step (b) validated before that row was processed.
- **The caller cannot name the money into a confirmation.** The new steps can only keep an observation, flag an order or record a return; none confirms, captures, refunds or moves fulfilment. The provider check still never confirms (D-68); `payment_process_event` still takes a ledger row id and nothing else.
- **Personal data.** None added: the audit rows carry statuses, amounts in paise, currencies, provider payment ids and ledger row ids — no name, address, email or phone.
- **Known limits.** 0009's own: (a) **A confirmation that came first stands.** Only the evidence processed before a timely matching signed capture decides: in every arrival order of that evidence the result is now the same (the harness's arrival-order sets; the integration block's), but a capture that takes the order's lock before the last piece of contradicting evidence confirms the order, and the confirmation stands (the 0005 record's contract 8) — a verified return of another payment after it flags it (0008), a signed failure of the confirming payment after it is `stale_failed`, a check listing it after it writes nothing, and that payment's own verified return after it writes its return row only. (b) **A payment Checkout reported and a signed failure named waits for a person, and the order offers no payment meanwhile.** The order is flagged at once (contracts 4 and 7) and its pages answer "being confirmed" — the customer is not invited to pay again beside the contradiction (the cost of the alternative: a second payment, then a review); nothing shows the review to staff before S1.9 / S2.2, so the owner resolves it from the records until then. Razorpay should not produce the contradiction (a valid Checkout signature is issued for a payment authorised in that session); when it does, the safe reading is a person's. A signed authorisation of the payment between the two changes nothing (the same review), and the payment's own later timely capture meets that review (`order_under_review`) and confirms nothing — a review no capture clears, as 0007 has it for a check that contradicts a signed failure; a capture processed before the contradiction is complete confirms, and the confirmation stands ((a)). (c) **A late authorisation that a check observes after its signed failure waits for a person** — the same cost as 0007's known limit (a), now also when a late signed authorisation has moved the payment's row past the failure before the check (the ledger read decides, not the row), in the safe direction (D-20, D-69): its timely capture is `order_under_review`. Without a check or a verified return, a late authorisation's capture confirms as before. (d) **The ledger read is unindexed.** At most one read per call — a provider check of an order that could be held whose listing raised no other review, or a payment's first verified return on such an order — scans the ledger's Razorpay rows for the payment's failure (`provider_events` has its primary key and the unique `(provider, event_id)` only); TEST held 426 Razorpay ledger rows, 32 of them `payment.failed` (read-only, 2026-11-28 15:30 UTC). Indicative, in the builder's local in-process Postgres (single-threaded): about 0.1 s per check at 200,000 ledger rows, against about 0.01 s under 0008. No index is added (this file changes no table): a store whose ledger grows that far wants a partial expression index on the payment entity's id where `provider = 'razorpay' and event_type = 'payment.failed'` — a later, additive migration (`PROJECT-STATUS.md` §10 #33). (e) **What arrived before the apply.** A provider check made under 0007 over a hold a signed authorisation raised kept no record, so a signed failure after it is still `stale_failed` for that order (unless a verified return of that payment was recorded — then `payment_state_conflict`, contract 4) — on TEST, 10 synthetic pending orders hold an `authorized_only` hold with no provider-check record, none of which can be told apart from an order no check ever saw; a verified return under 0005–0008 of a payment whose row a signed event had verified (created it, or moved a row the provider check created) was not recorded, and is not recorded later unless it is repeated after the apply. The ledger's signed failures processed before the apply ARE read: on TEST, three (AS-1512, AS-1626 and AS-1751) synthetic pending orders of earlier runs stand held by a signed authorisation with a stale signed failure in the ledger — a provider check of any of them, or a first verified return of their payment, is now the review. No order on TEST has a payment that a verified return reported and a signed failure failed (read-only, 2026-11-28 15:30 UTC); PROD has no order. Carried from the 0008 record, as it states them there: its (a) — the stale-failure rule needs a standing provider-check hold, now kept in both lock orders (and, for a payment a verified return reported, an order that could be held); its (b) — superseded by contracts 6 and 7 (a payment a signed event verified first is recorded, and judged, on its first return); its (c) — `order_not_payable` through a return reachable at S1.7 only by a direct write; its (d) — a flag only (no staff surface before S1.9 / S2.2, no refund before S2.4, no reconciler — D-68); its (e) — a return on an order awaiting its payment writes no review unless a signed failure of that payment was recorded (contract 7); its (f) — 0008's own past rows; and through it the 0007 record's (a)–(c).
