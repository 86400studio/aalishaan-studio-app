## What and why

`0003_staff_auth` is the database half of S1.2 (`docs/ROADMAP.md` S1.2; `docs/TECH-ARCHITECTURE.md` §4 row 0003, §5; `docs/THREAT-MODEL.md`). It does three things, all additive: (1) gives the staff row the state the server guard and the revocation path need — `mfa_enrolled_at` (informational, set when a TOTP factor is verified; the guard reads the Auth server's factor list, never this column), `revoked_at` and `revoked_reason` (set by `revokeStaffAccess`; a check keeps a revoked row from being active — `revoked_at is null or active = false`); (2) states the D-35 permission model in the database — the enum `permission_area` with the six areas of the final Admin and the immutable function `staff_permission_areas(staff_role)` returning `owner_admin` → all six, `operations` → work + catalogue, `support` → support, which `src/lib/staff/permissions.ts` mirrors and a hermetic test keeps equal (`tests/unit/staff-permissions.test.ts`); (3) adds the project's first row-level policy: `authenticated` gets SELECT on `staff_profiles` under `staff_profiles_select_own` — the member's own row (`user_id = auth.uid()`) and only at `aal2` (`auth.jwt() ->> 'aal'`), so no staff data is readable through a password-only session. Owner reads of other members stay on the server through the privileged client after the guard: the policy references no other table and no project function, so it cannot recurse and needs no `SECURITY DEFINER` helper.

Not in this file: Auth users (created by the admin API — the TEST tool on TEST, the owner at S3.3 on PROD; the app never offers sign-up), MFA factors and sessions (Supabase Auth's own tables), the audit rows (written by the server into the S1.1 `audit_log` — `staff.sign_in`, `staff.sign_in_failed`, `staff.mfa_enrolled`, `staff.role_changed`, `staff.access_revoked`, `staff.access_restored`), invitations and presets (S2.1, `0005_settings`). **No destructive operation** — no DROP, DELETE, TRUNCATE or type change in the forward file; no policy opens a table to `anon`; no `SECURITY DEFINER`.

### Contracts settled in step 1 (recorded here and in `docs/TECH-ARCHITECTURE.md` §5)

- **Session:** Supabase Auth cookies (`httpOnly`, `secure`, `sameSite=lax`, path `/admin`, name prefix `aalishaan-staff`) read by a per-request `@supabase/ssr` client with the publishable key; identity by `auth.getUser()` on every request; the assurance level from the validated token's claims; refreshed cookies written by `src/proxy.ts` on `/admin/:path*`.
- **Authorisation:** the active `staff_profiles` row read with the privileged client; its role mapped to areas by the pure model equal to this file's function; a route or action names its areas and every one must be held. The decision table is in `docs/THREAT-MODEL.md` §4.
- **Revocation:** `active = false`, `revoked_at`, `revoked_reason` (the server function or the TEST tool), then `auth.admin.updateUserById(..., { ban_duration: '876600h' })` so refresh stops, then the audit row — written once the staff row has changed, whatever the ban answered, and saying which; it records the state that was read before the change, never an assumed one. The guard reads the row on every request, so a revoked member is denied on the next request whatever their cookies say. Restoration (S2.1's Enable; the TEST tool's `--restore`) reverses the three writes with its own audit row. **Revocation does not delete the member's sessions:** while it stands nothing opens, but lifting it makes any session that has not expired usable again — so a restoration after a suspected compromise goes with a new password and a factor reset (`docs/THREAT-MODEL.md` §5; S2.1's Enable is written with this in mind).
- **Recovery route:** the human owner removes the lost TOTP factor in the Supabase dashboard (Authentication → Users → the user → Multi-factor → delete), or on TEST runs `pnpm db:test:staff-users --apply --reset-mfa`; the next sign-in forces a fresh enrolment and writes `staff.mfa_enrolled`. No code path skips MFA. Exercised on TEST in the VS Code leg (the sprint record records the run).
- **The S2.1 `active` flag:** Disable / Enable (S2.1) uses `active` without a revocation; the check constraint allows an inactive row without `revoked_at` and forbids an active row with it.

## Security check

- [x] Default-deny preserved: RLS stays enabled on `staff_profiles` (0002); the one policy allows SELECT of the caller's own row at aal2 and nothing else; no default-allow table ships.
- [x] Writes are owner-scoped — every write to `staff_profiles` is the server's, with the privileged client after the server guard's decision (at S1.2 the enrolment action, through `getStaffAccess`; `guardAction` from S2.1's first action on), or the TEST tool's on TEST; `authenticated` holds no write.
- [x] No anonymous read/write path added: `anon` gains nothing — no grant, no policy, no EXECUTE. (Like the two S1.1 enums, the new type `permission_area` keeps Postgres's default USAGE for `PUBLIC`: a type name, reachable through no object an anonymous caller can use. The SELECT grant covers every column of the member's own row, `revoked_reason` included — a member at aal2 may read why their own access was revoked; nobody else's row is ever visible.)
- [x] Privileged functions: `staff_permission_areas` is immutable, pinned to `search_path = ''`, not `SECURITY DEFINER`, reads no table, takes the role as its only argument and returns the mapping; EXECUTE revoked from `public` and `anon`, granted to `authenticated` and `service_role`.
- [x] No secret, key or connection string in the SQL, the PR or this record.

## Rollback plan

1. Stop or limit writes if continued traffic could compound the damage; record who authorised it. (At S1.2 nothing writes to these columns on PROD; on TEST the tool and the enrolment flow.)
2. Retreat the dependent code first (revert the PR / Vercel Instant Rollback): the S1.1 code is compatible with the 0003 shape (it never reads the new columns), so the schema may stay.
3. **Prefer keeping the additive schema and forward-fixing.** A schema rollback runs `0003_staff_auth.down.sql` by hand, on TEST first (the rehearsal above) and only then, with its own authorisation and by the human owner, on PROD; then `pnpm exec supabase migration repair --status reverted 0003 --project-ref <REF>`. The S1.2 code must be retreated first: with the columns gone every `/admin` request of a signed-in user answers the unavailable state. **From 0003 on, a rollback of the S1.1 files starts with this file:** the order is 0003, then 0002, then 0001 — `0002_orders.down.sql` drops the type `staff_role`, which the function `staff_permission_areas(staff_role)` depends on, so run alone it stops at that statement — and the ledger is repaired for each (`migration repair --status reverted 0003 0002 0001`).
4. Data: the down file deletes the three columns' values (MFA enrolment time, revocation time and reason); Auth users, factors, sessions and audit rows are untouched. A revocation recorded in `audit_log` survives; the `active` flag survives (it is a 0002 column), so a revoked member stays denied.
5. Verify schema and the affected flow (the sign-in refused with the unavailable state until the code is retreated; the S1.1 tables untouched); record the result.

Order matters: schema deploys before the code that depends on it; on rollback, code normally retreats first. **Host rollback does not restore the database, and down-SQL does not restore lost data.**

Never do this: never run the down file merely because it exists, never run it through `db push`, and never describe a rollback as complete until both schema and data impact have been verified.
