## What and why

A guest order is a contact, an address, an order with its number, its items, its immutable snapshot and its first payment attempt, and they must commit together or not at all. The server reaches Postgres through PostgREST only (`@supabase/supabase-js`; no direct driver), where one request is one transaction — so separate `.insert()` calls can never be atomic. `0004_checkout` makes the write one function call, and adds the smallest durable state the provider step needs so that a Razorpay call — which Postgres cannot roll back — is made exactly once per attempt and its uncertainty is recorded rather than guessed (`docs/sprint-prompts/S1.6-checkout-pending-order.md` §H.3; decisions D-60, D-61, D-62).

Not in this file: any table grant or policy (the 0002 default-deny stands; the functions run as the caller, `service_role`, with the privileges it already holds), any generic SQL entry point, an attempts table, a raw or encrypted token, new values in `orders.payment_status` or `payment_attempts.status`, an outbox row, stock or reservation fields, payment verification (S1.7), the expiry worker (S1.8), real charges or tax (S3.1).

### Contracts (each has a test — "Verification")

1. **One call, one transaction.** `checkout_create_pending_order(p_request jsonb)` validates, locks, recomputes and writes inside one PostgREST request. No `EXCEPTION` block exists anywhere in the file, so any failure aborts the statement and the transaction rolls back whole — the order number included (the 0002 counter row is updated by the order's own INSERT).
2. **Validation before anything is read or written, with fixed messages.** Structure, keys and every value shape are checked in the function with the same bounds as the 0002 table CHECKs, and refused as `checkout: invalid_request` under SQLSTATE `ZC001` — so a table CHECK (whose error detail would carry the failing row) never fires with a customer's data. All refusals are custom SQLSTATEs of class `ZC` (an implementation-defined class): `ZC001` invalid_request · `ZC002` attempt_payload_changed · `ZC003` sales_closed · `ZC004` rule_not_supported · `ZC005` item_unavailable · `ZC006` total_changed · `ZC007` policies_missing · `ZC008` amount_out_of_range · `ZC010` attempt_not_found · `ZC011` state_conflict · `ZC012` attempt_too_old · `ZC013` provider_time_out_of_range. The server maps the code alone (`src/lib/server/checkout/store.ts`) and never reads a message, detail or hint.
3. **Attempt ownership.** The browser mints a 32-byte random attempt key; the database holds only its SHA-256 (`orders.checkout_attempt_hash`, unique). Presenting the key is the only way to reach an attempt: no function looks an order up by email, phone, order number or id. The submitted bag and details are bound by an HMAC keyed with the attempt key itself (`checkout_payload_mac`), so the same key with other details is refused (`ZC002`) and a copy of the database alone holds no digest of personal data it could test. An advisory transaction lock on the attempt hash serialises concurrent submissions of one attempt; the second finds the first's order and returns it (`replayed = true`) without touching the counter.
4. **Plain INSERT for orders** (the 0002 rule): never `ON CONFLICT`. The replay lookup precedes the write, so no order row is ever absorbed after taking a number.
5. **The effective rule is read inside the transaction**: the latest `effective_from` not in the future, `version` as the tie-break. S1.6 accepts only a rule that is **open and marked synthetic** — a closed or missing rule is `ZC003`; a non-synthetic rule or an exclusive tax treatment is `ZC004`. Real sales need the owner's charges and tax (S3.1) and open by their own database change, never through this file. Unknown shipping stays NULL in the order (never zero); tax is written as NULL (no rate exists).
6. **Prices from the catalogue, under row locks.** The bought variants and their artworks are locked `FOR SHARE` for the transaction, then read; the locking statement must have locked one row per bought code (`variant_code` is unique, so no unlocked row can then match in the statements that follow — a row that became visible only after the lock is refused): an unknown code, an artwork that is not `Active`, a variant that is not `made_to_order` or not INR is `ZC005`. The total is recomputed and must equal the total the page showed (`ZC006`) — a precondition that can only refuse; no browser amount is ever written. A total under ₹1 or above the money bound is `ZC008`.
7. **The snapshot** carries the items as presented (code, finish, artwork title and slug, orientation, quantity, unit price, line total), the totals, the address, the rule's version and values, and the seven current policy versions (latest version per key not dated in the future; fewer than seven is `ZC007`) — and **not** the email address or the phone number. Existing policy versions are referenced; a checkout never creates one.
8. **A guest is always a new contact and a new address.** Nothing searches, reuses or updates a customer by matching email or phone (reviewed linking is S2.12).
9. **The provider step.** `payment_attempts.provider_order_state` moves only `intent → requested → linked | failed | unknown` and `unknown → linked | failed` (a guard trigger; NULL on rows that are not a checkout's order-creation row, so S1.7 may add per-payment rows). `checkout_claim_provider_create` is the single compare-and-set under the row lock: exactly one caller is answered `claimed = true`, and only that caller calls Razorpay. It refuses when the store has closed since (`ZC003`), when the order is not pending or is under review (`ZC011`), or when the order is older than its own rule's window (`ZC012`). `checkout_link_provider_order` stores the provider order id and the provider's own creation time and sets `orders.expires_at = that time + the pinned rule's minutes` in the same transaction — once (D-20); the same id again changes nothing, another id is `ZC011`, a provider time more than ten minutes before the order or ahead of the database clock is `ZC013`. `checkout_close_provider_create` records `failed` or `unknown` with a reason code, an optional review flag and one `audit_log` row; a linked attempt is never closed. Asked again for the outcome the attempt already holds, it changes nothing — unless it asks for a review the order does not have yet: the flag is then raised and audited, the state untouched (a link refused during recovery reaches the function exactly so; added before the first apply, from the pre-apply review of 2026-11-11). Lock order in all three: the payment attempt row, then its order (S1.7 follows it).
10. **Set-once fields** (a second guard trigger, binding `service_role` too): an order's attempt hash and payload MAC never change after insert; its token hash, its salt and a set `expires_at` are set once — the deadline is never extended.
11. **The confirmation link (D-61, amending D-09).** `confirmation_token_salt` is 32 random bytes per order; the link's token is `base64url(HMAC-SHA-256(ORDER_TOKEN_SECRET, label ‖ salt))`; the database stores the salt and the token's SHA-256 (`confirmation_token_hash`, the D-09 column), never the token. See "Security check".

## Security check

- **Privileges.** No function is `SECURITY DEFINER`; each has `set search_path = ''` and schema-qualified names. They run as `service_role` with the table privileges 0001/0002 already granted it — `SELECT … FOR SHARE` on `variants` and `artworks` uses its existing UPDATE privilege there; the inserts use its existing INSERT privileges; the order's number comes from the 0002 trigger. The publishable key (`anon`) and a signed-in staff member (`authenticated`) cannot execute any of them (42501), and no table grant changed, so the browser still reaches no order data.
- **No generic entry point.** No dynamic SQL (`EXECUTE`), no statement assembled from an argument. Every argument is a value compared or stored; the JSON request is read key by key and unknown keys are refused.
- **No personal data in errors or logs.** Refusals are fixed texts. The server logs enumerated reason codes only.
- **The derived link, honestly.** Whoever holds BOTH a copy of the database (the salts) and `ORDER_TOKEN_SECRET` can derive every order's link. Rotating the secret revokes no link already issued — `/order/[token]` (S1.7) verifies by the stored hash and needs no secret; rotation only changes what later derivations produce, so an order whose link must still be sent (S1.8) after a rotation needs its salt and hash re-issued. **Re-issue runbook (a suspected leak of the secret; a human decision, never automatic):** (1) set a new `ORDER_TOKEN_SECRET` in the affected Vercel scope and redeploy; (2) for each order whose link must be revoked, write a new salt and the matching new hash in one statement by a one-off, owner-authorised database change — the guard trigger makes both set-once, so this needs its own reviewed migration or an owner-run statement with the trigger disabled for that transaction; (3) send the new link through the normal channel. Until S1.7 no link is delivered to anyone, so the exposure at S1.6 is nil in practice.
- **Uncertainty is recorded, never resolved by assumption.** A provider answer that does not prove a refusal leaves the attempt `unknown`; nothing in this file or the server creates a second provider order for it, marks a payment failed or confirms anything. Only S1.7's verified events will.
- **Known limits.** (a) The rule is read, not locked: an order may commit in the instant a closing rule is being inserted; the claim re-checks the rule before any provider order is created, so no payment can start for a store that has closed. (b) `business_rules` has no tax rate, so an exclusive-tax rule is refused rather than computed. (c) An order whose provider create never linked has no `expires_at`; S1.8 treats it as unresolved, never as payable without limit.

## Apply procedure — PROD (human only)

After the independent review approves the candidate and before the merge: the owner, in their own terminal, runs `pnpm exec supabase migration list --project-ref <PROD_REF>`, `pnpm exec supabase db push --project-ref <PROD_REF> --dry-run`, reads that only `0004_checkout.sql` is listed, then `pnpm exec supabase db push --project-ref <PROD_REF>`, and afterwards verification 1–4 through the SQL editor or the read-only connector. **No rule is inserted on PROD**: its one rule stays the closed prelaunch row (the owner read it back on 2026-11-11: version 1, `sales_open = false`, `prelaunch`), `SALES_MODE` stays `off` there, and the functions are therefore inert in Production — the server's gate answers "closed" before any of them is called, and the create function itself refuses a closed rule.

## Rollback plan

Forward-fix first. The down file is run only on a written authorisation naming the file and the project, with the S1.6 application code rolled back first (without the functions every checkout answers "unavailable"; the storefront, the bag and the Admin are unaffected). It deletes the attempt bindings, link salts and provider-order states of every checkout order — after it, no customer can resume an attempt, no link can be derived for those orders, and which provider orders were linked, failed or left unknown is no longer recorded in the database (`orders.expires_at`, the orders themselves, their items, snapshots and audit rows stay). Afterwards: `pnpm exec supabase migration repair --status reverted 0004 --project-ref <REF>` for the same project.

## Fixture lifecycle

Every row the integration and e2e suites write through these functions is synthetic and retained: orders, order items, snapshots, addresses and audit rows cannot be deleted by any API role, and each order keeps its number. S1.7 and S1.8 must expect pending, linked, failed and unknown synthetic orders on TEST and select their own fixtures by the attempt hashes they create.
