## What and why

The independent review of the S1.7 candidate (`9260e64`, 2026-11-26) returned four findings that a rule under the database's own row locks, or evidence the ledger keeps from the first delivery on, must close — so none can be fixed in the server alone:

- **Finding 3 — every live payment counts.** The provider check was given one payment id picked from Razorpay's listing; a second live payment the listing showed was never recorded, so a timely signed capture of the first could confirm the order beside it. The check is now given **every** captured or authorised payment the provider listed, in one call, under the order's lock: more than one is a review no capture clears, and each payment is recorded as known.
- **Finding 4 — the observed money is judged and kept.** The read dropped the amount and the currency the provider observed, and the check wrote the stored intent's amount in INR on the payment's row. The check now receives the observed amount (exact paise) and currency of each payment and judges them as the event path does (0005 step (e)): another currency or an amount that is not both the order's total and the checkout row's amount is a review no capture clears, and the observed values are retained — on a row the check creates (INR, within bounds); an existing row keeps its amount and the review's audit row is the evidence.
- **Finding 6 — a repeated event's money is judged.** A signed authorised or captured event for a payment whose row was already there or further was called a duplicate by its status alone, so a contradicting event (another amount or currency for the same payment id) ended silently as `stale_authorized` and a later matching capture could confirm. Such an event is now the same payment again only when it states the money a signed event already recorded on the row; a contradiction is `currency_mismatch` / `amount_mismatch` — the review of 0005's step (g) — and the payment's row never moves back.
- **Finding 7 — the ledger keeps the verified bytes.** The webhook verified its HMAC over the raw bytes but ledgered only their parse, which `JSON.parse` and `jsonb` normalise (whitespace, key order, escapes, number text; an integer beyond 2^53 is rounded). `docs/TECH-ARCHITECTURE.md` §7 requires the payload "stored verbatim". The ledger now keeps the exact bytes that were verified beside their parse, immutably.

Not in this file: findings 1, 2 and 5 (server and page code only — `src/lib/server/checkout/flow.ts`, `src/lib/bag/purchased.ts`, `src/components/checkout/checkout-form.tsx`, `src/lib/schemas/order-confirmation.ts`); any table grant or policy; any change to `payment_return_state` or `order_confirmation_view`; the X-Razorpay-Signature header (not stored: an owner-chosen webhook secret may be short, and stored body/MAC pairs would allow an offline guess — an owner decision if ever wanted); re-parsing or cross-checking `raw_body` against `payload` in the database (a body the server accepted must never fail its ledger step forever); a refund, a cancellation or any scheduled work.

### Contracts (each has a test — "Verification")

1. **The verified bytes are kept, exactly, beside their parse.** `provider_events.raw_body bytea` — nullable, `octet_length` between 2 and 262144 (the webhook's `WEBHOOK_MAX_BODY_BYTES`). `payment_record_event(p_event_id, p_event_type, p_payload, p_raw_body)` writes `raw_body = p_raw_body` on both of its inserts (the event's row, and a derived row for other content); a call without bytes, or with fewer than 2 or more than 262144 of them, is `payment: invalid_request` (`ZP001`) and stores nothing. The server passes exactly the bytes the signature was verified over (`src/lib/server/payments/webhook.ts`), as bytea's hex input (`\x…`, `src/lib/server/payments/store.ts` `byteaHex`). `payload` stays the processing copy: `payment_process_event` reads nothing else.
2. **Identity is 0005's.** The same id with the same type and payload is the same event again: its row keeps the bytes of the delivery that stored it first (a redelivery in other bytes — other spacing — adds nothing). The same id with other content is kept beside the first under `<id>#<digest of the payload>`, with its own bytes. Rows stored before 0006 keep `raw_body` NULL; their redeliveries are the same event and add nothing.
3. **The bytes are immutable.** `protect_provider_event()` (0002's trigger function, re-created in place — the trigger `provider_events_protect` is not touched) refuses any change to `raw_body` (filling a NULL included) with the other ledger fields, and still refuses DELETE; the processing marks may still change.
4. **No verified delivery is ledgered without its bytes.** `payment_record_event(text, text, jsonb)` is dropped; the four-argument function is the only ledger step.
5. **A repeated event is the same payment again only with the same money.** In `payment_process_event` — 0005's body word for word except this branch — a repeated or older authorised or captured event of a payment whose row is already there or further compares its signed currency and amount with the row's (both written by a signed event, and judged against the order then): another currency is `currency_mismatch`, another amount `amount_mismatch` — the review of step (g): `needs_review = true`, `payment_hold = NULL` (a hold is replaced, so no later capture clears it), one audit row `payment.review.<reason>` with the event's own money and ledger row, outcome `review:<reason>`. The payment's row is left exactly as it is: its status only moves forward. Same-money repeats stay `duplicate_capture` / `stale_authorized` / `stale_failed`, silent. A failed event's money is judged on neither path (the forward path never judges it either). A confirmed order meeting such an event stays confirmed — flagged, with its one outbox row.
6. **The provider check is given every live payment and its money.** `payment_record_provider_check(p_payment_attempt_id, p_payments)`: `p_payments` is a JSON array of 1 to 99 objects (the most one page of the provider's listing holds — the read refuses a full page), each exactly `{id, status, amount_paise, currency}`: an id `^pay_[A-Za-z0-9]{6,60}$`, `captured` or `authorized`, exact positive paise as a decimal string, three upper-case letters; the ids distinct. Anything else is `ZP001`, before anything is read. The server sends every distinct live payment of the listing, strongest first, and a listing that contradicts itself about a live payment is "not known" (`src/lib/server/payments/reconcile.ts` `livePaymentsOf`) — the server compares no money itself.
7. **The same locks.** The checkout row (`ZP020` if none), then its order, then each payment's own row in id order — 0005's lock order (its contract 14).
8. **One matching payment is 0005's hold.** Exactly one live payment, in INR, for both the order's total and the checkout row's amount, on an order that awaits payment (linked, `pending`, `pending_payment`) and is under no review: `capture_unverified` (captured) or `authorized_only`, with one audit row `payment.hold.<hold>` (reason `provider_check`), whose `next.payment` now carries the observed `{status, amount_paise, currency}`. A captured answer replaces `authorized_only`; the same answer again changes nothing.
9. **More than one, or other money, is a review no capture clears.** In the event path's order of precedence — `currency_mismatch`, `amount_mismatch`, then `extra_payment` (more than one live payment) — on an order that awaits payment and is under no review or under a hold (a review replaces a hold, as step (g) does): `needs_review = true`, `payment_hold = NULL`, one audit row `payment.review.<reason>` (reason `provider_check`, `external_ref` the strongest payment — the first captured, else the first authorised, by id) whose `next.payments` lists every payment as observed. A later signed capture of any of them is then a review too (`extra_payment` beside another known payment, or `order_under_review`), never a confirmation and never a `send_confirmation` task. The answer is `held = false`, in 0005's shape.
10. **Each payment shown is recorded as known — never as paid.** A payment with no row gets one: status `created`, `signature_verified = false`, the observed amount — only where the row can hold it (INR, within the column's bounds; otherwise no row is written and the audit row is the evidence). A row that exists is left as it is. A payment id another order holds is `payment_conflict` (`ZP021`), and nothing of the call is kept — not even a row written for a payment listed before it.
11. **Never a confirmation, never a review replaced.** An order under a review that is not a hold, a confirmed order, an order no longer awaiting payment (failed, expired, its fulfilment moved on) or an unlinked attempt is left exactly as it is (`held = false`, nothing written). Nothing in the provider check or the ledger step confirms an order, queues work, moves an item or reads `business_rules`; `payment_process_event` keeps 0005's confirmation unchanged.
12. **House style and refusals.** plpgsql, `set search_path = ''`, never `SECURITY DEFINER`, no `EXCEPTION` block, no dynamic SQL; EXECUTE revoked from `public`, `anon` and `authenticated` and granted to `service_role` only, for all four functions. Every refusal is one of 0005's fixed texts under its custom SQLSTATE (no new code: the server's mapping is unchanged); the ledger guard keeps 0002's two `42501` refusals.

## Security check

- **Privileges.** No function is `SECURITY DEFINER`; each has `set search_path = ''` and schema-qualified names. They run as `service_role` with the table privileges 0002 already granted it. The publishable key (`anon`) and a signed-in staff member (`authenticated`) cannot execute any of them (42501), and no table grant changed: the browser still reaches no order, payment or event data, and `raw_body` is readable by `service_role` only.
- **No generic entry point.** No dynamic SQL, no statement assembled from an argument. The bytes are stored and never parsed, evaluated or returned by the database; `p_payments` is validated value by value, and its values are compared or stored.
- **The caller cannot name the money into a confirmation.** The provider check can raise a hold or a review, record payments as `created` and unverified, and nothing more; `payment_process_event` still takes a ledger row id and nothing else.
- **Personal data.** `raw_body` is a second copy of what the payload already holds — the provider's delivery, which can contain the payer's email and contact as Razorpay sends them: the evidence §7 requires, readable by `service_role` only, never logged or returned (S2.12's privacy work must cover it with the payload). Audit rows carry statuses, amounts in paise, currencies and provider ids — no name, address, email or phone.
- **Known limits.** (a) A review the provider check raises with nothing verified on record (two live payments, or another amount or currency, where no Checkout return was verified) leaves its payments known, not verified, and `payment_return_state` (unchanged here) does not count them as a payment on record. The checkout therefore asks Razorpay again — read-only, nothing recorded — on every later load of such an order (pending, under a review without a hold, no payment reported, authorised or captured, its attempt linked — `src/lib/server/checkout/flow.ts` `notPayable`): a captured or authorised payment is "being confirmed" (no pay button), a payment in flight or no usable answer "could not be checked", and only a listing with no live payment is "held" beside a usable form — what that page says rests on the provider's listing each time, not on a stored count (*until the re-review of round 1's fixes, 2026-11-26:* a later reload read such an order as "held" with the form usable; `tests/unit/payment-reconciliation.test.ts`, "a review the provider check raised, then a reload"). (b) If a payment's signed capture commits while the provider is being read, the order is already confirmed and the check writes nothing: the other payment is flagged by its own signed event (0005's `extra_payment`). (c) A `created` (in-flight) payment beside a live one is not counted as live — no money has moved yet; the check answers for live payments only. (d) A failed event's money is judged on neither path, by design. (e) A listed payment whose row is already `failed` (its signed `payment.failed` processed, then a late authorisation the provider now lists) stays `failed`: the check only tests an existing row for a conflict and never moves it, and the event path counts a payment as live only when its row has not failed (`v_other_live`). With it as the only listed payment the check raises the clearable hold, and a timely signed capture of another payment — from a Checkout window that was already open — can then confirm the order beside it; the listed payment is flagged by its own signed event (`extra_payment`), if that arrives. 0005 has the same gap (not a regression of this file); no SQL change at S1.7 — the comment at the check's loop says so. (f) Handed to S2.11 (changes, holds and cancellations): the first launch right after a link does not check the fulfilment status — nothing at S1.7 moves fulfilment off `pending_payment` while the payment is pending; and a cancelled order's page shows the closed state's wording (`ORDER_FAILED.closed`, NS-06: "The time to pay for this order has passed."), which is inexact for a cancellation.

## How the pinned CLI applies it

As one pipelined batch ending with the ledger insert (`supabase/README.md` → "What the CLI does"): a failing statement rolls the whole file back with its ledger row. The file has no statement that must run outside a transaction. `alter table … add column … add constraint` takes a brief exclusive lock on `provider_events` and validates the CHECK against the existing rows (all NULL). The two `drop function` statements fail loudly if 0005 is not applied (no `if exists`).

**The code and the database move together.** The S1.7 code at the head that carries this file calls the new signatures only; the code before it calls the replaced ones only. Between the two, either direction fails safe — PostgREST finds no matching function (`PGRST202`), the adapter answers `unavailable`: the webhook answers 503 (Razorpay delivers again), the provider check answers "could not be checked" (no new payment is offered), the Checkout return and the order page are unaffected. So: TEST is applied before the candidate's Preview is tested; PROD is applied by the owner (0005, then 0006) before the merge, while Production's payment gate stays closed.
