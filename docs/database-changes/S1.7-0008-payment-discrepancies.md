## What and why

The independent review of the S1.7 candidate at `4b8f779` (round 3, 2026-11-27) returned three Blocking findings. Two of them lie inside functions that `0007` and `0005` define — applied on TEST, so not editable — and only a rule under the database's own row locks (the checkout row, then the order, then the payment) can close them:

- **Finding 2 — an intervening signed authorisation could bypass the provider-hold conflict rule.** 0007's rule (its contract 1) sat in the forward path's failed branch only. When the provider API reported payment A captured (the `capture_unverified` hold) and A's signed `payment.authorized` then arrived (recorded beside the hold — `recorded:authorized`), A's row stood `authorized`, so A's signed `payment.failed` took the repeated-or-older branch — `stale_failed` — before the hold was looked at; A's timely signed capture could then confirm the order, advance its item and queue `send_confirmation`, where D-73 requires a person to review the contradiction. Now the same rule also holds in the repeated-or-older branch: a signed failure of the payment a standing provider-check hold names is `payment_state_conflict` whatever that payment's row says by then, and the row keeps its stronger signed status.
- **Finding 3 — a distinct verified payment return after confirmation could escape reconciliation.** After A's signed capture confirmed the order, a different payment B returned with a valid checkout signature for the same provider order: 0005's `payment_return_state` recorded B as reported with its ordinary `payment.return.verified` audit row and left the order unflagged, and the confirmed order's page never asks Razorpay about B (`src/lib/server/order-confirmation.ts` → `providerQuestionApplies`: an unflagged pending order only). With B's webhook lost, staff would get no review naming the possible extra payment. Now a payment that the verified return newly records for an order that no longer awaits its payment is a review: on a confirmed order, any payment but the one whose signed capture confirmed it (`extra_payment`); for an order whose fulfilment moved off `pending_payment`, or whose payment status is `expired` or `failed`, any payment (`order_not_payable`). Of the two remedies round 3 named — a durable discrepancy for staff, or a reconciliation through the existing bounded provider check — this file takes the first: the flag and its audit row, under the order's lock, in the return's own transaction.

Not in this file: finding 1 (the checkout page's code — `src/components/checkout/checkout-form.tsx` and `src/components/checkout/attempt-key.ts`); any change to `payment_record_event`, `protect_provider_event`, `payment_record_provider_check` or `order_confirmation_view`; any table grant or policy; a refund, a cancellation, a staff surface for reviews or any scheduled work.

**What 0008 amends.** The 0007 record's contract 1 (a signed failure that contradicts a live API observation of the same payment — now in the repeated-or-older branch too); the 0006 record's contract 5 (a same-money repeated `payment.failed` stays `stale_failed` — now except the failure of the payment a standing provider-check hold names); the 0005 record's contracts 8 and 9 (the same exception) and 10 (the verified return records, never confirms — and now also flags a discrepancy). Each of those records carries a dated note; nothing else of them changes.

## Security check

- **Privileges.** Neither function is `SECURITY DEFINER`; each has `set search_path = ''` and schema-qualified names. They run as `service_role` with the table privileges 0002 already granted it. The publishable key (`anon`) and a signed-in staff member (`authenticated`) cannot execute either (42501), and no table grant or policy changed: the browser still reaches no order, payment or event data.
- **No generic entry point.** No dynamic SQL, no statement assembled from an argument; `payment_return_state`'s two arguments are validated by 0005's patterns before use, and the new step compares and stores values only.
- **The caller cannot name the money into a confirmation.** The return's new step can only flag the order and audit the payment as reported; it never confirms, captures, refunds or moves fulfilment. `payment_process_event` still takes a ledger row id and nothing else.
- **Personal data.** None added: the audit rows carry statuses, amounts in paise, currencies, provider payment ids and ledger row ids — no name, address, email or phone.
- **Known limits.** 0008's own: (a) **The stale-failure rule needs a standing provider-check hold.** After a review has replaced the hold — the conflict itself, or any other review —, a later stale signed failure of that payment is `stale_failed` again, with no second audit row; the order is already flagged, and no capture clears its review (`order_under_review`). And once that payment's own timely capture has confirmed the order (the confirmation clears the hold), a later signed failure of it is `stale_failed` and flags nothing: the confirmation stands (the 0005 record's contract 8). (b) **The return's review needs a payment the return newly records.** A payment whose row a signed event already verified (`signature_verified = true` — its signed capture, for example) writes nothing new on its verified return: the event path judged it when it arrived (another payment's capture on a confirmed order is `review:extra_payment`). The review is written once per payment, the first time a return records it. *(2026-11-28 — superseded by 0009's contracts 6 and 7: a payment a signed event verified first is recorded, and judged, on its first verified return.)* (c) **`order_not_payable` through a return is reachable at S1.7 only by a direct write.** No S1.7 path leaves an uncaptured order off `pending` / `pending_payment` (the confirmation moves both together, and a captured order is `extra_payment`'s case) (the suite's case cancels its own synthetic order by one direct privileged write): S1.8's pending-order expiry job and S2.11's cancellations are the first that will. (d) **A flag only.** The confirmed order's own page still shows its confirmation (`orderPageState` reads the payment status first — `src/lib/schemas/order-confirmation.ts`); nothing shows the review to staff before S1.9 / S2.2, nothing refunds an extra payment (S2.4), and no reconciler job exists (D-68). (e) **A return on an order that awaits its payment writes no review** (contract 5): under a hold or not, the event path decides when that payment's events arrive (another payment's capture beside it is `extra_payment` — 0005's other-live rule: any other payment row of the order that has not failed; 0007 added only the standing-hold clause). *(2026-11-28 — amended by 0009's contract 7: unless the order could be held and a signed failure of that payment was recorded — then `payment_state_conflict`.)* (f) **0008 judges only what arrives after its apply.** A stale signed failure processed under 0007 beside a standing provider-check hold left that hold standing (0007's stale branch writes nothing), so that payment's timely capture would still confirm; and a verified return recorded under 0005–0007 after a confirmation stays unflagged (its repeat writes nothing — `v_recorded` false).
