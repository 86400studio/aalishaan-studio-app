## What and why

A captured payment must confirm its order exactly once, and the confirmation is five things that are true together or not at all: the payment's own row, the order's statuses and `confirmed_at`, its items' stage, one audit row and one unit of pending work for the confirmation message. The server reaches Postgres through PostgREST only (`@supabase/supabase-js`; no direct driver), where one request is one transaction — so separate writes can never be atomic, and a crash between them would leave a paid order unconfirmed, or a confirmed order with no message queued. `0005_payment_finalization` makes each step one function call (`docs/sprint-prompts/S1.7-razorpay-verification.md` §H.3; decisions D-67, D-68, D-21, D-20, D-09 as amended by D-61).

The one new column answers a question the existing `orders.needs_review` flag cannot: *may a later valid capture clear this review by itself?* A payment that is authorised but not yet captured, and a capture the provider's API shows before any signed event has arrived, are expected to resolve when the signed `payment.captured` event is processed. A wrong amount, an extra payment or a late payment are not. `payment_hold` names the first kind (`authorized_only`, `capture_unverified`); NULL beside `needs_review = true` is every other review and is never cleared by this file.

Not in this file: any table grant or policy (the 0002 default-deny stands; the functions run as the caller, `service_role`, with the privileges it already holds), any generic SQL entry point, new values in `orders.payment_status`, `orders.fulfilment_status` or `payment_attempts.status`, a refund or a cancellation of any kind, an order expiry job or any scheduled work (S1.8), the worker that executes `pending_work` or anything that sends a message (S1.8), a confirmation from the Checkout return or from the provider's API (D-68 — only a signed event confirms), stock or reservation fields, real charges or tax (S3.1).

Its record states them in full.

1. **Verified deliveries only reach the ledger, and the ledger comes first.** The server calls `payment_record_event(p_event_id, p_event_type, p_payload)` only after the webhook's HMAC has verified over the raw request bytes (`src/lib/server/payments/webhook.ts`): the row is written with `signature_ok = true` and the payload as delivered. 0002 makes `signature_ok` immutable and `(provider, event_id)` unique, so a row written for an unverified delivery would hold the genuine event's key for good — nothing unverified is ever inserted. The function has no business effect; it answers the row's id, whether it was inserted now, and its processing status.
2. **The same event id never overwrites.** `insert … on conflict (provider, event_id) do nothing`. The same id with the same type and payload is the same event again (the existing row is answered, `inserted = false`). The same id with other content is kept beside the first under `<id>#<first 32 hex characters of the SHA-256 of the payload>` (`derived = true`) and is processed like any other verified event. The id is Razorpay's `x-razorpay-event-id` header, or — when the header is absent or not of the accepted shape — `sha256:<hex of the raw body>`, so a retry of the same bytes always meets its own row. Accepted shapes: id `^[A-Za-z0-9_.:-]{1,120}$`, type `^[a-z][a-z0-9_.]{1,118}$`, payload a JSON object; anything else is `payment: invalid_request` (`ZP001`).
3. **One event, one effect, one transaction, from the ledger row alone.** `payment_process_event(p_event uuid)` takes nothing but the ledger row's id: the amount, currency, payment id and provider order id are read from the stored payload, never from the caller. It locks the ledger row first, so a concurrent delivery of the same event waits and then reads the row's marks; a row already `processed` or `ignored` answers its recorded outcome with `replayed = true` and changes nothing. The row's marks (`processing_status`, `processed_at`, `processing_note`) are written in the same transaction as the effect, last — an event is never marked processed before its effect commits. No `EXCEPTION` block exists anywhere in the file, so any failure aborts the statement and the transaction rolls back whole, the ledger row staying `received` for the provider's retry.
4. **Only `payment.captured` confirms, and only an eligible order.** The order is found through the checkout's own payment-attempt row that holds the provider's order id (0004's unique index over checkout rows) — never by amount, receipt, time or a row that is not a checkout's. The confirmation needs all of: the entity says `status = captured` and `captured = true`; the order is `payment_status = pending` and `fulfilment_status = pending_payment`; the currency is INR; the amount equals both `orders.total_paise` and the checkout row's `amount_paise` (integer paise); no other payment of the order is known and not failed — authorised or captured by a signed event, reported by a verified Checkout return, or shown by the provider check (contract 11) (*before 2026-11-23:* only an authorised or captured one counted, so the capture of a second payment could clear a hold raised for the first — the builder's review, H.8); `orders.expires_at` is set and the event's own ledger time (`provider_events.received_at` — the database's clock when the delivery was stored) does not pass it (D-20); and the order is under no review other than a hold. Then, together: the payment's row `captured`; the order `payment_status = captured`, `fulfilment_status = confirmed`, `confirmed_at = now()`, `needs_review = false`, `payment_hold = NULL`; its items `stage 0 → 1`; one `audit_log` row `payment.captured.confirmed`; one `pending_work` row.
5. **One unit of pending work per order.** Kind `send_confirmation`, entity `order` / the order's id, dedupe key `send_confirmation:order:<order id>`, payload `{"v": 1}` — no token, no address, no contact (S1.8 derives the link at send time from the order's salt and `ORDER_TOKEN_SECRET`, D-61). `insert … on conflict (dedupe_key) do nothing`, then the row under that key must be this order's own confirmation task; a foreign row under the key stops the confirmation whole (`payment: outbox_conflict`, `ZP030`) and nothing of it commits.
6. **Everything else is recorded and flagged — never confirmed, never refunded, never used to bring an order back.** In this order of precedence, each with one `audit_log` row `payment.review.<reason>` naming the payment and the ledger row, the order flagged `needs_review = true` with `payment_hold = NULL`: `extra_payment` (the order is already captured, or another payment of it is live) · `order_not_payable` (the order no longer awaits payment) · `currency_mismatch` · `amount_mismatch` · `expiry_missing` (a capture for an order with no deadline) · `late_capture` (the event was stored after the deadline) · `order_under_review` (a valid capture for an order under a review that is not a hold) · `payment_conflict` (the payment id already sits on a row that is not this order's payment row — nothing is rebound). A captured or authorised event whose provider order id no checkout row holds flags no order and guesses none: its audit row `payment.review.unknown_reference` is tied to the ledger row (`entity_type = provider_event`) and counts the non-checkout rows that carry the same id; a failed event for an unknown reference is ignored.
7. **An authorised payment is a hold, not a confirmation.** `payment.authorized` for the right order and amount, with nothing else in the way, sets `needs_review = true`, `payment_hold = authorized_only` and one audit row `payment.hold.authorized_only`; its own capture later confirms and clears it. An authorised payment with a mismatch is a review (contract 6), not a hold.
8. **A payment's row only moves forward** — `created → failed → authorized → captured`. A repeated or older event of a payment whose row is already there or further has no effect (`duplicate_capture`, `stale_authorized`, `stale_failed` — *2026-11-27, amended by 0008: except a failure of the payment a standing provider-check hold names, a `payment_state_conflict` review — the note above; 2026-11-28, amended by 0009: that hold's record now kept over a hold a signed authorisation raised too, and, for an order that could be held, the failure of a payment a verified Checkout return reported is the same review — the note above*); a failed payment that is later captured (a late authorisation) is captured. Per-payment rows are `payment_attempts` rows with `provider_order_state IS NULL` — the shape 0004 left free for exactly this — so the checkout's own row and its guard trigger are untouched. A currency other than INR or an amount outside the column's bounds is never written to the row as something else, and a row that already exists is then left exactly as it was: the ledger and the audit row carry what the event said (*before 2026-11-23:* an existing row was advanced under its old amount and currency — H.8).
9. **`payment.failed` leaves the order as it is** — recoverable while its deadline stands *(2026-11-27 — amended by 0007: except the failure of the payment a standing provider-check hold names, a `payment_state_conflict` review — the note above; amended by 0008: a repeated or older failure of that payment too, after a stronger signed status; 2026-11-28 — amended by 0009: and, for an order that could be held, the failure of a payment a verified Checkout return reported, the check's record now kept over a hold a signed authorisation raised too)*. Other event types (`order.paid` included) are kept in the ledger and end `ignored` (`unsupported_event`); a payment event whose entity is not of the expected shape ends `ignored` (`malformed_payment`). Neither has a business effect.
10. **The verified Checkout return records, never confirms.** `payment_return_state(p_attempt_hash, p_verified_payment_id)` answers where an attempt's order stands (its number, statuses, flag and hold, its deadline, the salt and hash of its confirmation link, how many of its payments are reported / authorised / captured / failed, the database's time). With a payment id — passed only after the server has verified Checkout's signature over the **stored** provider order id and that payment id — the payment is first recorded as reported: a row with status `created` and `signature_verified = true`, once, with one audit row `payment.return.verified`. It never sets authorised, captured or paid. *(2026-11-28 — amended by 0009: once per payment by that audit row, whatever created the payment's row — the note above.)* A payment id held by another order is refused (`ZP021`); an attempt that is not linked is refused (`ZP012`); no such attempt answers NULL. *(2026-11-27 — amended by 0008: a payment it newly records for a confirmed order — any but the confirming one — or for an order no longer awaiting its payment also flags the order once, with one review audit row — the note above.)*
11. **The provider's API can hold, never confirm (D-68).** `payment_record_provider_check(p_payment_attempt_id, p_payment_id, p_provider_status)` — called after the server has asked Razorpay which payments an order has — raises `capture_unverified` (the API shows a captured payment) or `authorized_only` on an order that still awaits payment and is under no other review, with one audit row `payment.hold.<hold>` (reason `provider_check`), and records the payment it was shown as known: that payment's own row, status `created`, `signature_verified = false`, the checkout row's amount in INR — never authorised, captured or paid. The capture of another payment of the order then meets that row as a live payment (an extra payment, contract 4) and never clears this hold. A payment id another order holds is refused (`ZP021`) before anything is written, and nothing of the call is kept. The same answer again changes nothing; a captured answer replaces the weaker `authorized_only`; an order under any other review is left exactly as it is. Only the signed captured event confirms, and it clears the hold it finds. *(Amended by 0006 and, 2026-11-27, by 0007 — the notes above: an order under another review, a confirmed order and an order no longer awaiting payment now get a review with every payment as observed.)* *(2026-11-28 — amended by 0009, the note above: over a hold that already stands, a signed authorisation's included, the check keeps its observation once as the provider-check hold record; a processed signed failure of the listed payment in the ledger is the `payment_state_conflict` review for an order that could be held.)*
12. **A hold never stands without its flag.** `orders_payment_hold_with_review` (`payment_hold is null or needs_review`) and `orders_payment_hold_allowed` (the two values). Whoever else raises `needs_review` on an order that carries a hold sets the column to NULL in the same UPDATE (the column's comment says so, for S2.2 and S2.4).
13. **The one read path of `/order/[token]`.** `order_confirmation_view(p_token_hash)` answers by the SHA-256 of the presented token only — no lookup by order number, email or id exists: the order's number, statuses, flag and hold, its deadline, its totals in paise, the items exactly as the purchase snapshot holds them, the payment counts, the SHA-256 of its checkout attempt key (so the browser that placed the order can recognise it; the key itself is never stored) and, for the server only, the checkout row's id, state and provider order id. **No contact and no address.** NULL when no order has the token. It reads; it never writes.
14. **Lock order**, everywhere: the ledger row (in `payment_process_event` only), then the checkout's payment-attempt row, then its order (0004's order), then the payment's own row.
15. **Refusals are fixed texts under custom SQLSTATEs** of class `ZP` (an implementation-defined class): `ZP001` invalid_request · `ZP010` event_not_found · `ZP012` state_conflict · `ZP020` attempt_not_found · `ZP021` payment_conflict · `ZP030` outbox_conflict. The server maps the code alone (`src/lib/server/payments/store.ts`) and never reads a message, detail or hint.
16. **A confirmation never depends on the sales gate.** `payment_process_event` does not read `business_rules`: an order created while intake was open confirms when its timely capture arrives after intake has closed. (The server's half — the webhook is governed by the provider's configuration and identity, not by `SALES_MODE` — is `src/lib/server/payments/config.ts`.)

## Security check

- **Privileges.** No function is `SECURITY DEFINER`; each has `set search_path = ''` and schema-qualified names. They run as `service_role` with the table privileges 0002 already granted it (SELECT / INSERT / UPDATE on `orders`, `payment_attempts`, `provider_events` and `pending_work`; SELECT / INSERT on `audit_log`; UPDATE on `order_items`). The publishable key (`anon`) and a signed-in staff member (`authenticated`) cannot execute any of them (42501), and no table grant changed, so the browser still reaches no order, payment or event data.
- **No generic entry point.** No dynamic SQL (`EXECUTE`), no statement assembled from an argument. Every argument is a value compared or stored; the event payload is stored as delivered and read at fixed paths.
- **The caller cannot name the money.** `payment_process_event` takes a ledger row id and nothing else; `payment_return_state` and `payment_record_provider_check` cannot move a payment to authorised or captured or an order to paid, whatever they are given.
- **No personal data in errors, logs or the outbox.** Refusals are fixed texts; audit rows carry statuses, amounts in paise, the currency and provider references — no name, address, email or phone; the outbox payload is `{"v": 1}`. The ledger keeps the provider's payload as delivered (it can contain the payer's email and contact as Razorpay sends them): that is the evidence `docs/TECH-ARCHITECTURE.md` §7 requires, it is readable by `service_role` only, and it is never logged or returned.
- **The order view is the token's alone.** It answers by the token's hash, returns no contact and no address, and the server re-checks the stored hash against the presented token's hash in constant time before using the answer (`src/lib/server/order-confirmation.ts`).
- **Uncertainty is recorded, never resolved by assumption.** An API answer raises a hold; a missing deadline is a review; an unknown reference is audited against the ledger row with no order guessed. Nothing here refunds, cancels or expires anything.
- **Known limits.** (a) The deadline is judged by when the delivery was *stored*: a payment made in time whose event first reaches the server after the deadline (a long provider outage, a webhook that was mis-configured for a while) is review-only by design (D-20) — a person decides, nothing is refunded automatically. **This includes the lost-webhook recovery itself (D-68):** an event that Razorpay's Technical Support replays at the owner's request after the order's deadline is stored at replay time, so it ends as `review:late_capture` even when the provider check raised the `capture_unverified` hold in time — the hold becomes that review, and the order is confirmed by no function in this file (*before `86bb63c`, 2026-11-26:* "an event that the owner replays from Razorpay's Dashboard after the order's deadline"). Recovery therefore completes automatically only while the deadline stands (Razorpay's own retries in the first hour, or a replay within it); after it, it ends in a persisted, audited review a person resolves (the Admin's review queue is S2.2). Whether evidence recorded in time — the hold, or a payment reported by a verified return — should let a late-stored signed capture confirm was open as **D-69** — decided by the owner on 2026-11-23: kept as built (Option A; `PROJECT-STATUS.md` §8a); S1.8 may weigh it again with its expiry job. (b) An order under a review that is not a hold is never confirmed automatically, even by a perfectly valid later capture: the payment's row is captured, the audit row says `order_under_review`, and the resolution is a person's (the Admin's review queue is S2.2, refunds S2.4). Until then the customer's page says the payment is being checked. (c) A `capture_unverified` hold is cleared only by the signed event stored before the deadline (limit (a)); if Razorpay's retries all fail, the owner ~~replays the event from the Razorpay Dashboard~~ requests that event's individual replay from Razorpay's Technical Support (D-68; *corrected 2026-11-27 — the S1.7 record → H.15, H.16:* the tested account offers no Dashboard replay control; the route and its conditions are `docs/HANDOFF.md` §4) — no scheduled reconciler exists, and none is assigned to S1.8. (d) No expiry job exists yet: an unpaid order past its deadline keeps `payment_status = pending` in the database until S1.8; the page and the finalizer compare the deadline with the database's clock themselves. (e) A payment's row is looked up under a row lock before it is inserted, and both functions that insert one take the checkout row's lock first, so the event and the verified return of one order are serialised. `payment_attempts` is unique on `(provider, provider_payment_id)` (0002), so two transactions of *different* orders that first see the same new payment id at the same instant cannot both insert: the second fails on the unique index, its transaction rolls back whole (the webhook answers "unavailable"), and the provider's retry then finds the row and records the conflict. The integration suite's concurrency cases are the proof on a real database.

## How the pinned CLI applies it
