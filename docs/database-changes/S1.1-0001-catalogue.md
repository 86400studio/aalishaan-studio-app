## What and why

`0001_catalogue` creates, in this order: (1) the enum `public.artwork_status` — `Draft`, `In review`, `Active`, `Hidden`, `Retired` (the final Admin displays Hidden as "Paused" and Retired as "Archived" — display labels, D-33); (2) `collections` (slug, name, intro, sort order), `art_styles` (slug, name, full name, intro, its collection, sort order), `frame_finishes` (the three codes `white` / `black` / `antique-gold` with their display names and the locked order), `artworks` (slug, title, full title, hook — the editor's "Short introduction", description, collection, art style, orientation, the locked facets rooms / moods / palettes, up to four palette hues, suggested frame — the editor's "Default frame", featured, the editor's free-text lead time (null until OI-03), SEO title, SEO description, the default image description, the artwork page's stage-image alt, status, published_at, the workbook source row), `artwork_images` (the eight named public slots per artwork at 480 / 1200 or the artwork itself, with the bucket object path, the prototype source path and its SHA-256), `variants` (one per artwork and finish: `variant_code` = `<slug>:<finish>`, `price_paise` as exact bigint paise, INR, availability, lead time); (3) `updated_at` triggers and the `enforce_variant_code()` trigger function (the variant code must equal `<artwork slug>:<finish code>`, the storefront's approved bag key); (4) default deny on every table through `lock_down_table` with an explicit revoke-then-grant of the four DML privileges to `service_role` only; (5) the view `public_catalogue` — the only anonymous read path: an explicit column allow-list over Active artworks with their variants and images as JSON, `security_barrier`, owned by the migration role (not `security_invoker`), SELECT granted to `anon`, `authenticated` and `service_role` after revoking the platform's default privileges; (6) the public bucket `catalogue-public` (public URL reads; 5 MiB; `image/webp` only; no `storage.objects` policy, so anonymous and authenticated clients can neither list, upload, update nor delete through the API).

S1.1 needs it because every later page (S1.4, S1.5) renders from this projection and checkout (S1.6) recomputes prices from `variants.price_paise` — browser values are display only (`SECURITY-CHECKLIST.md` §9 rule 5). The catalogue identities, the paise money model and the status vocabulary are things that cannot change after the first real order (`docs/ROADMAP.md` → Ordering rationale). **No destructive operation** — no DROP, DELETE, TRUNCATE or type change in the forward file; no policy opens a table to `anon` or `authenticated`; no `SECURITY DEFINER`; no auth, job, network or retention object. The one row the file inserts is the bucket's own row in `storage.buckets`.

Design decisions beyond the roadmap's field list (step 1 of the S1.1 prompt — "map approved source fields"): `full_title`, `palette_hues` and `image_alt_text` are stored because the approved artwork pages render them (the hero descriptor, the "Colours in this artwork" swatches and the stage-image alt — `prototype/scripts/build-products.cjs`); they are approved copy from `products.json` and the workbook, not new facts. `lead_time` exists on both artworks and variants as nullable free text and is seeded null (no customer promise, OI-03). The facet lists, the finish codes and the orientation values are check constraints (locked facts); a new value needs a decision and a migration. `source_row` is a seed reference and is not projected.

## Files

- Up-SQL: `supabase/migrations/0001_catalogue.sql`
- Down-SQL: `supabase/rollbacks/0001_catalogue.down.sql` — reverses exactly the schema: drops the view, the triggers, the trigger function, the six tables in dependency order, the type, then **deletes the bucket's objects and the bucket row** (this deletes every catalogue row and image and cannot restore them; the seed and the upload recreate them). It refuses to run while `0002_orders` references the catalogue (`order_items` → `variants`, `artworks`): reverse 0002 first. It lives outside `supabase/migrations/` on purpose and is never executed because it exists (see "Rollback plan").
- Access policy changes (RLS/policies) included in the same PR: yes — RLS **enabled with no policy** on all six tables (default deny, through `lock_down_table`); `REVOKE ALL … FROM public, anon, authenticated` (the helper) and `REVOKE ALL … FROM service_role` followed by `GRANT SELECT, INSERT, UPDATE, DELETE … TO service_role` on each table (the platform's default privileges would otherwise also give it REFERENCES, TRIGGER and TRUNCATE); on the view `REVOKE ALL … FROM public, anon, authenticated, service_role` then `GRANT SELECT … TO anon, authenticated, service_role`; EXECUTE on `enforce_variant_code()` revoked from `public`, `anon`, `authenticated` and granted to `service_role` (trigger use); **no `storage.objects` policy** for the bucket (intentional: public URL reads need none; every API write and listing is denied without one). `FORCE ROW LEVEL SECURITY` is deliberately not set.

## Security check

- [x] Default-deny preserved: every table is created and locked down in the same file through the S0.2 helper; no default-allow table ships. The platform's `ensure_rls` event trigger (`ENVIRONMENT-PARITY.md` §7.4) also enables RLS on each `CREATE TABLE` in `public` — inventoried below, neither relied on nor altered.
- [x] Writes are owner-scoped — **N/A by design at S1.1**: no user-reachable write path exists; the server's `service_role` key (which bypasses RLS) is the only writer — the seed, reset and upload tools, and from S2.5 the staff editors through their own server actions and the 0003 policies.
- [x] No anonymous read/write path added unintentionally: the one intentional anonymous read is `SELECT` on `public_catalogue` — an explicit allow-list over Active rows only (no id, status, source row or timestamp other than `published_at`; no customer data exists in this migration); the base tables stay denied at the grant level and the RLS level; public bucket reads are by URL of the enumerated object paths only. The projection test (`tests/unit/catalogue.test.ts` on the SQL; `tests/integration/catalogue.test.ts` on TEST) proves the exact column set.
- [x] Privileged functions: `enforce_variant_code()` is pinned to `search_path = ''`, not `SECURITY DEFINER`, EXECUTE revoked from `public`, `anon`, `authenticated` and granted to `service_role` only for trigger use; it reads no argument as authorisation. The view is owner-privileged by design (documented above) and `security_barrier`, so a caller's predicate can never see a non-Active row.
- [x] No secret, key or connection string in the SQL, the PR or this record.

**Platform behaviour inventoried (S0.2 Deviation 24 carry-over):** both projects carry the event trigger `ensure_rls` (`ddl_command_end` on CREATE TABLE, CREATE TABLE AS, SELECT INTO) → `public.rls_auto_enable()` — owner `postgres`, `SECURITY DEFINER`, `search_path = pg_catalog`, EXECUTE granted to PUBLIC, `anon`, `authenticated` and `service_role` — which enables RLS on every table created in `public` and logs it; its definition is identical on TEST and PROD (md5 `6998ea6b4c2480f5d2e34b5dcf3f8d36`). Decision for S1.1: **documented, not managed** — the migrations keep enabling RLS themselves through `lock_down_table`, so the platform trigger is redundant, never load-bearing, and is not altered (replacing or revoking platform code casually would be a change outside this sprint's remit). The broad EXECUTE grant lets an API role *call* the function, which only ever enables RLS on a table the caller already created — `anon` and `authenticated` can create no table, so there is nothing to tighten; the verification block records the advisor's view when the owner runs it (`supabase-dev` → the Security Advisor, read-only) and any finding goes to the record.

select c.relname, c.relrowsecurity, c.relforcerowsecurity,
       (select count(*) from pg_policies p where p.schemaname = 'public' and p.tablename = c.relname) as policies

## Rollback plan

1. Stop or limit writes if continued traffic could compound the damage; record who authorised it. (At S1.1 nothing writes to these tables except the seed, reset and upload tools on TEST — stop running them.)
2. Retreat the dependent code first (revert the PR / Vercel Instant Rollback) when the prior code is compatible with the current schema — it is: the S1.1 application code never reads these tables at runtime.
3. **Prefer keeping the additive schema and forward-fixing.** If a schema rollback is unavoidable, a human runs `0002_orders.down.sql` and then `0001_catalogue.down.sql` by hand, on TEST first (the rehearsal above) and only then, with its own authorisation, on PROD; then records the reversal in the ledger with `migration repair --status reverted`.
4. Data: the down file deletes every catalogue row and bucket object; on TEST they are recreated by the seed and the upload; on PROD at S1.1 the tables are empty, and from S3.3 on a rollback would need the S3.3 catalogue-loading procedure to be repeated — state that plainly in the record if it happens. The Free plan holds no backup (D-05).
5. Verify schema, policies and the affected flow (`public_catalogue` absent after a rollback); record what was and was not restored.

Order matters: schema deploys before the code that depends on it; on rollback, code normally retreats first. **Host rollback does not restore the database, and down-SQL does not restore lost data.**

Never do this: never run the down file merely because it exists, never run it through `db push`, and never describe a rollback as complete until both schema and data impact have been verified.
