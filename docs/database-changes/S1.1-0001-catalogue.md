## What and why

`0001_catalogue` creates, in this order: (1) the enum `public.artwork_status` — `Draft`, `In review`, `Active`, `Hidden`, `Retired` (the final Admin displays Hidden as "Paused" and Retired as "Archived" — display labels, D-33); (2) `collections` (slug, name, intro, sort order), `art_styles` (slug, name, full name, intro, its collection, sort order), `frame_finishes` (the three codes `white` / `black` / `antique-gold` with their display names and the locked order), `artworks` (slug, title, hook — the editor's "Short introduction", description, collection, art style, orientation, the locked facets rooms / moods / palettes, up to four palette hues, suggested frame — the editor's "Default frame", featured, the editor's free-text lead time (null until OI-03), SEO title, SEO description, the default image description, the artwork page's stage-image alt, status, published_at, the workbook source row), `artwork_images` (the eight named public slots per artwork at 480 / 1200 or the artwork itself, with the bucket object path, the prototype source path and its SHA-256), `variants` (one per artwork and finish: `variant_code` = `<slug>:<finish>`, `price_paise` as exact bigint paise, INR, availability, lead time); (3) `updated_at` triggers and the `enforce_variant_code()` trigger function (the variant code must equal `<artwork slug>:<finish code>`, the storefront's approved bag key); (4) default deny on every table through `lock_down_table` with an explicit revoke-then-grant of the four DML privileges to `service_role` only; (5) the view `public_catalogue` — the only anonymous read path: an explicit column allow-list over Active artworks with their variants and images as JSON, `security_barrier`, owned by the migration role (not `security_invoker`), SELECT granted to `anon`, `authenticated` and `service_role` after revoking the platform's default privileges; (6) the public bucket `catalogue-public` (public URL reads; 5 MiB; `image/webp` only; no `storage.objects` policy, so anonymous and authenticated clients can neither list, upload, update nor delete through the API).

S1.1 needs it because every later page (S1.4, S1.5) renders from this projection and checkout (S1.6) recomputes prices from `variants.price_paise` — browser values are display only (`SECURITY-CHECKLIST.md` §9 rule 5). The catalogue identities, the paise money model and the status vocabulary are things that cannot change after the first real order (`docs/ROADMAP.md` → Ordering rationale). **No destructive operation** — no DROP, DELETE, TRUNCATE or type change in the forward file; no policy opens a table to `anon` or `authenticated`; no `SECURITY DEFINER`; no auth, job, network or retention object. The one row the file inserts is the bucket's own row in `storage.buckets`.

Design decisions beyond the roadmap's field list (step 1 of the S1.1 prompt — "map approved source fields"): `palette_hues` and `image_alt_text` are stored because the approved artwork pages render them (the "Colours in this artwork" swatches and the stage-image alt — `prototype/scripts/build-products.cjs`); they are approved copy from `products.json` and the workbook, not new facts; the owner accepted both on 2026-10-06. **`full_title` is not stored** (removed 2026-10-06 on the owner's decision, before any apply): no approved page shows it. The draft of this record said the artwork pages render it as a "hero descriptor"; that was read from a template line in `build-products.cjs` (line 77) which the 22 generated pages do not contain — across the 60 storefront pages of the prototype the full title and its descriptor appear only inside embedded script data, never in a page's text or attributes (checked 2026-10-06). `lead_time` exists on both artworks and variants as nullable free text and is seeded null (no customer promise, OI-03). The facet lists, the finish codes and the orientation values are check constraints (locked facts); a new value needs a decision and a migration. `source_row` is a seed reference and is not projected.

### Known limits (recorded 2026-10-06 from the pre-apply audit; none blocks S1.1 — each is assigned)

- **The variant code follows the slug only on writes to `variants`.** The trigger fires on INSERT and on UPDATE of `artwork_id`, `finish_code` or `variant_code`; `artworks` carries no guard, so a later change of an artwork's slug would leave its three codes behind. Nothing in S1.1 changes a slug. The product editor (S2.5, which has a "URL slug" field) must rewrite the codes in the same transaction or refuse the change, in its own migration.
- **An image row's path is checked for shape, not against its own row.** `object_path` must look like `artworks/<slug>/<slot>-<size>.webp`, but nothing ties it to that row's `slot`, `size_label` or artwork; the 330 seeded rows are consistent (the manifest test). The S2.5 media work owns a stricter rule if it writes these rows.
- **A style's collection is not enforced on the artwork.** `artworks.collection_id` and `artworks.art_style_id` are independent foreign keys; only the seed checks that a style stays inside one collection. S2.5 decides the rule when the editor can move either.
- **An Active artwork with no variants or images yields NULL arrays in the view**, and the mirror requires exactly 3 and 15, so one incomplete Active artwork fails a whole-list parse. The seed inserts an artwork before its images and variants, so an interrupted seed leaves that state until it is re-run. S1.4 / S1.5 decide how a reader treats an incomplete row (parse row by row, or leave it out).
- **Caching of the public images.** The object paths carry no version, so a replaced image keeps its URL. The upload sets a one-hour cache lifetime for that reason (the cloud draft set one year). The lasting rule — a version in the path, or a short lifetime — is settled with the pages that render these URLs (S1.5) and the replacement flow (S2.5).

## Files

- Up-SQL: `supabase/migrations/0001_catalogue.sql`
- Down-SQL: `supabase/rollbacks/0001_catalogue.down.sql` — reverses exactly the schema: drops the view, the triggers, the trigger function, the six tables in dependency order and the type (this deletes every catalogue row and cannot restore them; the seed recreates them). **It does not touch Storage: the bucket `catalogue-public` and its objects stay.** Current Supabase Storage refuses a SQL DELETE on `storage.objects` and `storage.buckets` — statement-level triggers (`protect_objects_delete`, `protect_buckets_delete` → `storage.protect_delete()`, error 42501 "Direct deletion from storage tables is not allowed. Use the Storage API instead."; statement-level, so they fire even when no row matches — Storage's own migration `0055-prevent-direct-deletes`, read in the public `supabase/storage` source on 2026-10-06; their presence on TEST is confirmed read-only in Verification 3) — and a SQL delete would in any case orphan the stored files (Supabase's "Delete Objects" guide). The forward file's bucket insert is `on conflict (id) do nothing`, so 0001 re-applies cleanly with the bucket as it is; whoever needs the images gone empties and deletes the bucket through the Storage API (the dashboard) under its own authorisation. (The cloud draft ended the file with two such SQL deletes; removed 2026-10-06 before any run.) The file refuses to run while `0002_orders` references the catalogue (`order_items` → `variants` and `frame_finishes`): reverse 0002 first. It lives outside `supabase/migrations/` on purpose and is never executed because it exists (see "Rollback plan").
- Access policy changes (RLS/policies) included in the same PR: yes — RLS **enabled with no policy** on all six tables (default deny, through `lock_down_table`); `REVOKE ALL … FROM public, anon, authenticated` (the helper) and `REVOKE ALL … FROM service_role` followed by `GRANT SELECT, INSERT, UPDATE, DELETE … TO service_role` on each table (the platform's default privileges would otherwise also give it REFERENCES, TRIGGER and TRUNCATE); on the view `REVOKE ALL … FROM public, anon, authenticated, service_role` then `GRANT SELECT … TO anon, authenticated, service_role`; EXECUTE on `enforce_variant_code()` revoked from `public`, `anon`, `authenticated` and granted to `service_role` (trigger use); **no `storage.objects` policy** for the bucket (intentional: public URL reads need none; every API write and listing is denied without one). `FORCE ROW LEVEL SECURITY` is deliberately not set.

- [x] Default-deny preserved: every table is created and locked down in the same file through the S0.2 helper; no default-allow table ships. The platform's `ensure_rls` event trigger (`ENVIRONMENT-PARITY.md` §7.4) also enables RLS on each `CREATE TABLE` in `public` — inventoried below, neither relied on nor altered.
- [x] Writes are owner-scoped — **N/A by design at S1.1**: no user-reachable write path exists; the server's `service_role` key (which bypasses RLS) is the only writer — the seed, reset and upload tools, and from S2.5 the staff editors through their own server actions and the 0003 policies.
- [x] No anonymous read/write path added unintentionally: the one intentional anonymous read is `SELECT` on `public_catalogue` — an explicit allow-list over Active rows only (no id, status, source row or timestamp other than `published_at`; no customer data exists in this migration); the base tables stay denied at the grant level and the RLS level; public bucket reads are by URL of the enumerated object paths only. The projection test (`tests/unit/catalogue.test.ts` on the SQL; `tests/integration/catalogue.test.ts` on TEST) proves the exact column set.

The view is owner-privileged by design (documented above) and `security_barrier`, so a caller's predicate can never see a non-Active row.
- [x] No secret, key or connection string in the SQL, the PR or this record.

**Platform behaviour inventoried (S0.2 Deviation 24 carry-over):** both projects carry the event trigger `ensure_rls` (`ddl_command_end` on CREATE TABLE, CREATE TABLE AS, SELECT INTO) → `public.rls_auto_enable()` — owner `postgres`, `SECURITY DEFINER`, `search_path = pg_catalog`, EXECUTE granted to PUBLIC, `anon`, `authenticated` and `service_role` — which enables RLS on every table created in `public` and logs it; its definition is identical on TEST and PROD (md5 `6998ea6b4c2480f5d2e34b5dcf3f8d36`). Decision for S1.1: **documented, not managed** — the migrations keep enabling RLS themselves through `lock_down_table`, so the platform trigger is redundant, never load-bearing, and is not altered (replacing or revoking platform code casually would be a change outside this sprint's remit). The broad EXECUTE grant lets an API role *call* the function, which only ever enables RLS on a table the caller already created — `anon` and `authenticated` can create no table, so there is nothing to tighten; the verification block records the advisor's view when the owner runs it (`supabase-dev` → the Security Advisor, read-only) and any finding goes to the record. **The advisor's view, read on TEST on 2026-10-06 before the apply:** two WARN items for this function — "Public Can Execute SECURITY DEFINER Function" (`anon_security_definer_function_executable`, lint 0028) and "Signed-In Users Can Execute SECURITY DEFINER Function" (`authenticated_security_definer_function_executable`, lint 0029) — beside the one INFO for `system_checks`. Both pre-date S1.1 (the function is the platform's, on both projects since they were created; it returns `event_trigger`, its ACL is `{=X/postgres,postgres=X/postgres,anon=X/postgres,authenticated=X/postgres,service_role=X/postgres}`). The decision stands — documented, not managed. Revoking EXECUTE on it from `anon` and `authenticated` would clear the two warnings; that is a change to platform code and an owner decision for a later migration, not taken in S1.1.

```sql
-- RLS on, not forced, no policy, on every S1.1 catalogue table
select c.relname, c.relrowsecurity, c.relforcerowsecurity,
       (select count(*) from pg_policies p where p.schemaname = 'public' and p.tablename = c.relname) as policies
  from pg_class c
 where c.relnamespace = 'public'::regnamespace and c.relkind = 'r'
   and c.relname in ('collections','art_styles','frame_finishes','artworks','artwork_images','variants')
 order by 1;                                                          -- true, false, 0 for each
-- table ACLs (a=insert r=select w=update d=delete; D=truncate x=references t=trigger m=maintain must be absent for service_role).
-- Each table: exactly {postgres=arwdDxtm/postgres,service_role=arwd/postgres}; the view: the owner plus
-- anon=r/postgres, authenticated=r/postgres, service_role=r/postgres; no other entry anywhere.
select c.relname, c.relacl::text from pg_class c
 where c.relnamespace = 'public'::regnamespace and c.relkind in ('r','v')
   and c.relname in ('collections','art_styles','frame_finishes','artworks','artwork_images','variants','public_catalogue')

-- the same as a yes/no matrix, for every table of the schema (21 after both files: system_checks, 6 here, 14 in 0002):

select c.relname,
       has_table_privilege('anon', c.oid, 'select, insert, update, delete, truncate, references, trigger, maintain') as anon_any,
       has_table_privilege('authenticated', c.oid, 'select, insert, update, delete, truncate, references, trigger, maintain') as authenticated_any
  from pg_class c where c.relnamespace = 'public'::regnamespace and c.relkind = 'r' order by 1;
-- the view's options and owner
select c.relname, c.relowner::regrole::text, c.reloptions from pg_class c where c.oid = 'public.public_catalogue'::regclass;  -- postgres, {security_barrier=true}
-- the trigger function: not SECURITY DEFINER, empty search_path, EXECUTE as intended
select p.proname, p.prosecdef, p.proconfig = array['search_path=""'] as search_path_empty,
       has_function_privilege('anon', p.oid, 'execute') as anon_execute,
       has_function_privilege('authenticated', p.oid, 'execute') as authenticated_execute,
```
