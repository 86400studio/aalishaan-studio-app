## What and why

`0002_orders` creates, in this order: (1) `refuse_change()` — the BEFORE UPDATE OR DELETE trigger function that raises `42501` and thereby makes a table append-only for every role, the server's `service_role` included; (2) the enum `staff_role` (`owner_admin`, `operations`, `support` — D-35) and `staff_profiles` (`user_id` → `auth.users`, role, display name, active; no row seeded — real users arrive with S1.2); (3) `business_rules` (version PK; effective date; approver by name and, once staff exist, by id; `synthetic`; `sales_open` with its reason `prelaunch` / `capacity` — exactly one of open or reason, D-37; the D-20 expiry in minutes as a rule; nullable shipping paise and tax treatment until OI-02 / OI-03) and `policy_versions` (the seven policy keys, version, title, intro, the sections as JSON, `terms_status` pending / effective, the source) — both append-only; (4) `customers_contact` (email and/or an Indian mobile, name; `synthetic` marks harness rows) and `addresses` (the address as entered, Indian PIN code, country IN — append-only: a correction is a new row); (5) `order_number_counter` (one locked row from 1001) and `next_order_number()`, `orders` (order number assigned by the insert trigger and immutable; five separate statuses — payment, fulfilment, support, refund, settlement; exact paise subtotal, nullable shipping and tax, total = the exact sum; the applied rule version; the D-09 `confirmation_token_hash`; a database-bumped `version`; `expires_at`; `needs_review`; `synthetic`; placed / confirmed timestamps) with `assign_order_number()` and `guard_order_update()`, `order_items` (the variant as purchased with its unit price in paise, quantity 1–99, the generated line total, the item's stage 0–10) and `purchase_snapshots` (one immutable JSON snapshot per order with the policy version ids and the rule version); (6) `payment_attempts` and the `provider_events` ledger (unique per provider and event id; `signature_ok`; DELETE refused and the ledger fields immutable through `protect_provider_event()`, processing marks mutable); (7) `pending_work` (the transactional outbox with a unique `dedupe_key`, status, retry bounds) and `work_history` (append-only); (8) `audit_log` (insert-only); (9) default deny on every table with narrow, explicit `service_role` grants after a `REVOKE ALL` (no TRUNCATE anywhere; no UPDATE or DELETE where the table is append-only).

S1.1 needs it because checkout (S1.6), payment verification (S1.7), the worker (S1.8) and every Admin slice write into these shapes, and the money model, the numbering, the ledger and the audit log must exist before anything writes to them (`docs/ROADMAP.md` → Ordering rationale; `SECURITY-CHECKLIST.md` §9 rules 3, 4, 5, 7). **No destructive operation** — no DROP, DELETE, TRUNCATE or type change in the forward file; no policy opens a table to `anon` or `authenticated`; no `SECURITY DEFINER`.

### Contracts settled in step 1 (recorded here and in `docs/TECH-ARCHITECTURE.md`)

- **Numbering (D-09):** `orders.order_number` = `'AS-' || n`, issued by `next_order_number()` from the single locked row of `order_number_counter` (`UPDATE … RETURNING` inside the inserting transaction — concurrent inserts serialise on the row lock; an aborted insert rolls the counter back, so numbers are unique and gapless from `AS-1001`). It is not a Postgres sequence or identity (nextval never rolls back). The BEFORE INSERT trigger assigns it and **refuses a caller-supplied value** (`23514`); the BEFORE UPDATE trigger refuses a change. EXECUTE on the function is granted to `service_role` only; `anon` and `authenticated` hold neither EXECUTE nor INSERT on `orders` — there is no anonymous allocation path (the prompt: "No anonymous allocation RPC").
- **The confirmation token (D-09, settled as `orders.confirmation_token_hash`):** S1.6 generates an opaque token of at least 256 random bits (`crypto.randomBytes(32)`, base64url-encoded, ~43 characters) and stores only its **lower-case hex SHA-256** (64 characters; check `^[0-9a-f]{64}$`; unique; NULL until issued). The raw token appears only in the customer's `/order/[token]` URL and the S1.8 confirmation email; S1.7 verifies a presented token by hashing it the same way and comparing in constant time; it is never stored, logged or returned by any API. Issuance and the route are S1.6 / S1.7.
- **The initial approver without a staff Auth user:** `business_rules.approver_name` is text (`'Delivery lead (86400 Studio)'` for version 1) and `approver_staff_id` is a nullable FK to `staff_profiles` filled from S1.2 on; no Auth user is invented.
- **Money:** every money column is `bigint` paise bounded to 100,000,000,000; `currency = 'INR'`; `orders.total_paise = subtotal + coalesce(shipping, 0) + coalesce(tax, 0)` as a check constraint, with shipping and tax NULL until the owner's inputs — never zero as a guess (D-PRE-13). The Zod mirrors (`src/lib/schemas/`) accept a safe-integer number, a decimal string or a bigint and yield a `bigint`; an unsafe or fractional value is refused, never coerced.
- **Immutability for every role:** the triggers fire regardless of the caller, so even the server's secret key cannot update or delete a snapshot, a policy or rule version, an address, a history row or an audit row, or delete or rewrite a provider event; TRUNCATE is revoked from `service_role` on every table.
- **Statuses:** `payment_status` ∈ pending / captured / failed / expired; `fulfilment_status` ∈ pending_payment / confirmed / in_production / shipped / delivered / part_delivered / on_hold / cancelled (the order summary states of locked-facts §9); `support_status` ∈ none / open / resolved; `refund_status` ∈ none / requested / partial / refunded; `settlement_status` ∈ not_settled / provider_settled / bank_matched / disputed; `order_items.stage` 0–10 = the eleven Admin stages. Check constraints, so a later sprint extends a vocabulary with a migration.

- [x] Default-deny preserved: every table is locked down in the same file; no default-allow table ships (the platform's `ensure_rls` trigger is inventoried in the 0001 record and not relied on).
- [x] Writes are owner-scoped — **N/A by design at S1.1**: no user-reachable write path exists; the server's `service_role` key is the only writer (the checkout server action, the webhook handler and the worker from S1.6–S1.8, the integration suite on TEST); customers never hold a session (D-PRE-03); staff policies arrive with 0003.

## Fixture lifecycle on TEST (the S1.1 prompt, step 5)

- The seed writes the catalogue, the policy versions, the rule version and `fixture:baseline`; it is idempotent (natural keys; a second dry run reports every row unchanged).
- The integration suite writes synthetic contacts (`synthetic = true`, `@example.test` addresses), orders (`synthetic = true`) and the rows that hang off them; it removes what the schema allows it to remove (contacts without references are deletable; orders, items and attempts are updatable but their snapshots, audit rows and history are append-only by design) and otherwise leaves **retained synthetic history** that the record names. The order numbers those rows consumed are gone for good on TEST (gapless means consumed, not reusable) — PROD is never seeded or tested this way.
- `pnpm db:test:reset --namespace=catalogue:` deletes the seeded catalogue rows only while no order item references a seeded variant and no seeded artwork carries a status the seed did not set; it never touches policy versions, rule versions, orders or ledgers.
- The only path that clears retained synthetic history is the rollback rehearsal (0001 record): the owner, with scoped delegation to the builder for the TEST project, runs the down files, repairs the ledger and re-applies; cadence: before an acceptance run of the Launch Gate (S3.2) and after an interrupted fixture run — never an unattended destructive reset.

## Rollback plan

1. Stop or limit writes if continued traffic could compound the damage; record who authorised it. (At S1.1 nothing writes to these tables on PROD; on TEST only the seed and the integration suite.)
2. Retreat the dependent code first (revert the PR / Vercel Instant Rollback) when the prior code is compatible with the current schema — it is: the S1.1 application code never reads these tables at runtime.
3. **Prefer keeping the additive schema and forward-fixing.** A schema rollback runs `0002_orders.down.sql` (then `0001_catalogue.down.sql` if that is also reversed), by hand, on TEST first (the rehearsal) and only then, with its own authorisation, on PROD; then `migration repair --status reverted 0002`.
4. Data: the down file deletes every row of the fourteen tables; on PROD at S1.1 they hold only the counter row; **once a real order exists the down file is never run** — a defect is fixed forward (an additive migration), never by deleting orders. State plainly in the record what was and was not restored if it ever happens.
5. Verify schema, functions and the affected flow (`orders` absent after a rollback; `next_order_number()` absent); record the result.

Order matters: schema deploys before the code that depends on it; on rollback, code normally retreats first. **Host rollback does not restore the database, and down-SQL does not restore lost data.**

Never do this: never run the down file merely because it exists, never run it through `db push`, and never describe a rollback as complete until both schema and data impact have been verified.
