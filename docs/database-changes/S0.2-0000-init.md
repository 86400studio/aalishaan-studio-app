## What and why

`0000_init` creates, in this order, (1) `public.set_updated_at()` — a BEFORE UPDATE trigger function that sets `updated_at = now()`; (2) `public.lock_down_table(regclass)` — the default-deny helper: `ALTER TABLE … ENABLE ROW LEVEL SECURITY` and `REVOKE ALL PRIVILEGES … FROM public, anon, authenticated`, with the target rendered from a `regclass` so no untrusted text reaches the DDL; (3) `public.system_checks` — `id uuid` primary key, a unique namespaced `check_key`, `status` limited to `ok` / `degraded` / `failed`, `synthetic boolean`, a bounded `note`, `created_at` / `updated_at`, the `updated_at` trigger, locked down through (2) and granted explicitly to `service_role` only. It is the table `GET /api/health` reads (status only) and the home of the S0.2 harness's namespaced synthetic fixtures (`fixture:`, `integration:`, `s0-2-proof:`); the S2.20 probes add their own namespace later. S0.2 needs it to prove, before any product table exists (S1.1), that Preview writes land only in TEST, that anonymous access is denied by default, and that the migration, client-boundary and harness tooling work end to end (`docs/ROADMAP.md` S0.2). **No destructive operation** — no DROP, DELETE, TRUNCATE or type change anywhere in the forward file; no policy opens the table to `anon` or `authenticated`; no `SECURITY DEFINER`; no auth, product, storage, job, network or retention object.

## Files

- Up-SQL: `supabase/migrations/0000_init.sql`
- Down-SQL: `supabase/rollbacks/0000_init.down.sql` — reverses exactly the schema: drops the trigger, the table (**this deletes every `system_checks` row and cannot restore them**), then the two functions, in reverse order. It lives outside `supabase/migrations/` on purpose: `supabase db push` discovers only that folder, so forward discovery can never run it, and it is never executed because it exists (see "Rollback plan").
- Access policy changes (RLS/policies) included in the same PR: yes — RLS **enabled with no policy** on `public.system_checks` (default deny); `REVOKE ALL PRIVILEGES ON TABLE public.system_checks FROM public, anon, authenticated`; `GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE public.system_checks TO service_role` (explicit, not left to default privileges); `REVOKE EXECUTE` on both functions `FROM public, anon, authenticated, service_role`. `FORCE ROW LEVEL SECURITY` is deliberately not set (the owner's dashboard role keeps its normal access for verification; no API role is affected either way).

## Security check

- [x] Default-deny preserved: `system_checks` is created with RLS enabled and no policy, through the helper, in the same file; no default-allow table ships.
- [x] Writes are owner-scoped — **N/A by design**: the table is server-only; no user-reachable write path exists. Only the server's `service_role` key (`SUPABASE_SECRET_KEY`, which bypasses RLS) writes, from `src/lib/server/setup-proof.ts` (Preview-only, token-guarded) and the trusted local fixture tools.
- [x] No anonymous read/write path added: none, intentionally — the publishable key is denied at the grant level and at the RLS level. `GET /api/health` reads through the server and returns a status, never a row; since Codex round 1 it also runs the same read with this build's publishable key on the server and answers `ok` only if that read, on the same project as the privileged identity, is denied by Postgres `42501` (or returns an explicit empty array while the privileged read saw a row); a schema-missing or malformed answer is not denial (Codex round 2) — the deployed proof of this box.
- [x] Privileged functions: both pinned to `search_path = ''`; neither is `SECURITY DEFINER`; EXECUTE revoked from `public`, `anon` and `authenticated` on both; `service_role` keeps EXECUTE on `set_updated_at` only (an explicit grant: the trigger fires for the server's DML, and a trigger function cannot be called as a plain function, so nothing is opened) and has none on `lock_down_table` (only the migration role, the owner, can call it); `lock_down_table` takes a `regclass`, so an unknown table fails at the cast and identifiers are quoted by Postgres, never built from text; neither function reads an argument as authorisation.
- [x] No secret, key or connection string in the SQL, the PR or this record.

## How the pinned CLI applies it (verified in the CLI's source at 2.117.0 on 2026-09-25)

- Discovery: files in `supabase/migrations/` matching `^([0-9]+)_(.*)\.sql$`, in directory order; `0000_init.sql` → version `0000`, name `init`. The only file the CLI skips is a **14-digit** `<timestamp>_init.sql` older than `20211209000000` (the legacy dashboard init), which this file is not — verified by `tests/unit/baseline-inventory.test.ts`, and visible in `supabase db push --dry-run` / `supabase migration list`.
- Execution: `db push` compares the folder with the remote ledger and, for each pending file, sends its statements as **one pipelined batch that ends with the ledger insert** (`INSERT INTO supabase_migrations.schema_migrations(version, name, statements)`). The extended protocol runs the pipeline as one implicit transaction, so a failing statement rolls back the file and its ledger row together; statements that cannot run inside a transaction (`CREATE INDEX CONCURRENTLY` and the like) would be sent on their own — the baseline has none. The connection is `RESET ALL` before each file.
- The dashboard SQL editor runs a pasted script as one implicit transaction too, but writes **no ledger row** (the human PROD procedure below prefers the CLI for that reason and documents the manual ledger insert as the fallback).

## Rollback plan

1. Stop or limit writes if continued traffic could compound the damage; record who authorised it. (At S0.2 nothing writes to `system_checks` except the harness — stop running it.)
2. Retreat the dependent code first (revert the PR / Vercel Instant Rollback) when the prior code is compatible with the current schema — it is: the S0.1 code ignores the table entirely.
3. **Prefer keeping the additive schema and forward-fixing.** If a schema rollback is unavoidable, a human runs `supabase/rollbacks/0000_init.down.sql` by hand in the SQL editor, on TEST first and only then, with its own authorisation, on PROD; then records the reversal in the ledger with `pnpm exec supabase migration repair --status reverted 0000 --project-ref <REF>`.
4. Data: the down file deletes every `system_checks` row; at S0.2 those are synthetic harness rows only, and the Free plan holds no backup, so nothing is restored — state that plainly in the record if it happens.
5. Verify schema, policies and the affected flow (`GET /api/health` returns `schema_missing` after a rollback); record what was and was not restored.

Order matters: schema deploys before the code that depends on it; on rollback, code normally retreats first. **Host rollback does not restore the database, and down-SQL does not restore lost data.**
