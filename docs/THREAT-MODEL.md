# THREAT-MODEL.md — Staff Access, Trust Boundaries and the Guard

Written at S1.2 (2026-10-12) for the `/close` skill and every later Admin sprint: what the staff side protects, who can reach it, where the trust boundaries sit and which invariants every merge keeps. It states the model as built; a change to the model is a reviewed change to this file and to `docs/TECH-ARCHITECTURE.md` §5 in the same PR. Customer-side threats (payments, tracking, public writes) are covered by `docs/SECURITY-CHECKLIST.md` §5 and §9 and by the sprints that build those paths (S1.6, S1.7, S1.9).

## 3. Trust boundaries

1. **Browser → server.** Nothing in the browser decides anything. The prototype's role preview, hidden role select, sample access code and local staff records are presentation and were never ported (D-32e). The browser holds the session only as `httpOnly`, `secure`, `sameSite=lax` cookies scoped to `/admin` (`src/lib/server/staff-session.ts`, `STAFF_COOKIE_OPTIONS`) that no script can read.
2. **Cookie → identity.** A cookie is a claim, not an identity. The guard asks the Auth server (`auth.getUser()`) on every request; a forged, expired or revoked token yields no user, and an Auth server that cannot be reached or does not answer as itself yields the unavailable state, never "no user" (`classifyAuthFailure`). The assurance level is the `aal` claim of the token the Auth server has just validated — decoded locally by auth-js from the same cookie-held token, in the same request, after `getUser()` (the order is what makes it trustworthy and is pinned by `tests/unit/staff-access.test.ts`); the factors come from the user object the Auth server returned.
3. **Identity → staff member.** An Auth user is a staff member only through a `staff_profiles` row read with the privileged client, with `active = true` and a role the model knows. The owner creates these rows (the TEST tool on TEST; the owner by hand on PROD at S3.3; the Staff & Access UI at S2.1). Sign-up is never offered: the app contains no sign-up call, and the project setting "Allow new users to sign up" is off (owner, Gate 0 #11 on TEST; S3.3 on PROD).
4. **Staff member → authorisation.** The role maps to the six permission areas (`src/lib/staff/permissions.ts` = `public.staff_permission_areas()`); a route or action names the areas it requires and every one must be held (`decideAccess`, `src/lib/staff/access.ts`). The server guard's decision is taken for every page render and inside every server action — an action reached from a page that already passed is still refused if the session has changed since. One decision function, three entry points: `guardAdminPage` in a content page (it redirects or returns the honest state); `getStaffAccess` in the sign-in, verification and enrolment pages and in their actions, which must act on the decisions that are not `allowed`; `guardAction` for the actions later sprints add (it has no caller at S1.2). RLS mirrors the role as the second layer (S1.2: the own-row policy at aal2; later sprints add their policies).
5. **Server → database.** The privileged client bypasses RLS and is used only after the guard's decision — except for the one audit row named in §1, which the sign-in form writes for a refused password before any session exists; it never reads a request cookie or header; it is created per call and never shared. The cookie client carries the publishable key and the member's own session, so RLS applies to anything it reads.
6. **Preview → TEST, Production → PROD.** The public values must point at the project the privileged identity resolved for the deployment context (`cookieClientConfig`), or the request is refused as unavailable: a Preview can never authenticate staff against PROD. The TEST tools refuse a PROD ref before any request.

## 4. The guard, in one table

| Facts established | Decision | What the member sees |
|---|---|---|
| Configuration, Auth or database unavailable | `unavailable` | "Not available right now" — never a pass |
| No user behind the cookies | `login` | redirected to `/admin/login` with a validated `next` |
| A user with no `staff_profiles` row (or a row of another user, or an unknown role) | `not_staff` | "No studio access" and a sign-out control; the sign-in actions end the session themselves |
| The Auth server refuses the member's own token because the user is banned (revocation bans the Auth user) | `revoked` | "Access revoked" and a sign-out control — the same state, reached before any staff row is read; only a request that carries the banned member's own valid token is answered this way |
| An inactive row (revoked or disabled), or a row that carries a revocation time | `revoked` | "Access revoked" and a sign-out control — on the very next request |
| No verified TOTP factor | `enrol` | the enrolment page, and nothing else |
| A session below aal2 | `verify` | the verification page |
| A required area the role does not hold | `forbidden` | "Access restricted" (the final Admin's heading); nothing protected is read |
| Everything above satisfied | `allowed` | the page or the action, with the staff identity |

The table is a pure function with a unit test per row and for the order of the rows (`tests/unit/staff-access.test.ts` — a revoked member or an account without a staff row can never reach the verification or enrolment step); the same file runs the session module that gathers the facts against fakes (every failure to establish a fact → `unavailable`). The S1.2 acceptance denials (Operations and Customer support each denied the owner-only section and the finance route) are rows of it and real Preview routes (`tests/e2e/admin-access.*.spec.ts`).

## 5. Threats and controls

| Threat | Control | Evidence |
|---|---|---|
| Password guessing through this app's sign-in form | The Upstash throttle counts every attempt — 5 per address per 15 minutes, 20 per client address — before the password is checked, and fails **closed** (no names, no network, any error → the sign-in is refused with an honest notice). The address is given one spelling (trimmed, lower-cased) before it reaches the throttle, the audit hash and the Auth server, so two spellings of one address cannot be counted separately. Addresses reach Redis as SHA-256 only (unsalted: not stored in clear, but someone who can read the database can test a known address against a key). Once an account has enrolled, its password alone never yields a staff session (MFA). | `src/lib/server/login-throttle.ts`; `login/actions.ts`; `tests/unit/login-throttle.test.ts`; the Preview check at the limit (VS Code leg) |
| Password guessing sent straight to the project's Auth API (the URL and publishable key are public values) | Not this app's throttle — those requests never reach it or `audit_log`. The controls are the Auth server's own per-address rate limits (the project's settings, recorded names-only for P9) and MFA: a guessed password still meets the second factor. The Auth server's CAPTCHA setting is an option for S3.2. | `ENVIRONMENT-PARITY.md` §7.5 (P9) |
| A stolen password | TOTP is mandatory; a session below aal2 reaches only the verification page; an account without a verified factor can only enrol — and only a staff account with a password session can enrol | the guard; `tests/unit/staff-access.test.ts`; `tests/e2e/auth.setup.ts` (which also proves on the Preview that a password session opens nothing) |
| Code guessing after a stolen password | Each six-digit code tried against a member's authenticator counts against that member in Upstash — 5 per 15 minutes, counted right or wrong before the Auth server sees it, failing closed — and a refused code writes its own audit row (`staff.sign_in_failed`, `code_rejected`), so a run of guesses is both bounded and visible. The Auth server's own limit on the code step is by client address, and from a server that address is the platform's, not the attacker's — which is why the app counts per member. | `consumeCodeAttempt`; `verifyTotp`; `tests/unit/login-throttle.test.ts` |
| First enrolment — trust on first use | **Residual risk, by design:** until a member has enrolled a factor — after the account is created, and again after the recovery route removes a factor — whoever holds that account's password can enrol their own authenticator and is that member at aal2. Procedure: create (or recover) and enrol in one sitting; change the password as part of every recovery; never hand a new account a password someone else knows. S2.1's invitations and the S3.3 procedure for the first Production owner are written with this in mind. | this file; `startEnrolment`, `confirmEnrolment` |
| A third party locking a known address out | **Accepted risk:** the per-address counter counts every attempt, whoever makes it, so six requests per quarter hour keep a known address — the single owner account included — throttled, and using up the Upstash plan's quota would refuse every sign-in (fail closed). Nothing is exposed by it; the owner's recourse is to wait out the window or clear the keys in the Upstash console. Turnstile or a platform firewall rule in front of the form is the S3.2 option. Accepted by the owner on 2026-10-13 (no Turnstile on the staff sign-in at launch — `TECH-ARCHITECTURE.md` §7). | `login-throttle.ts`; `TECH-ARCHITECTURE.md` §7 |
| Audit rows caused without signing in | Each refused password the throttle lets through writes one permanent `staff.sign_in_failed` row with the privileged client before any session exists — the one privileged write outside the guard. Bound: 20 per client address per 15 minutes (5 per address tried); unbounded across many client addresses. The row holds a hash, never an address. Accepted by the owner on 2026-10-13 with the throttle as the only brake; revisited with the protection tests of S3.2 (Turnstile, or writing the row only for addresses that are staff accounts). | `signIn`; `staff-audit.ts` |
| A stolen session cookie | `httpOnly` + `secure` + `sameSite=lax`, path `/admin`; the Auth server is asked on every request; revocation denies on the next request and the Auth ban stops refresh. **Lifetime:** the cookie is persistent (the SSR package sets 400 days and renews it on every refresh) and no code limits the age of a verified session — how long a browser stays signed in at aal2 is the Auth project's session settings (time-box, inactivity timeout), recorded with P9; a shared or lost device stays signed in until sign-out, revocation or that setting ends the session. Every later staff-only route (private files, exports) must live under `/admin`, where the cookie is sent. | `STAFF_COOKIE_OPTIONS`; `revokeStaffAccess`; the revocation exercise on TEST; `ENVIRONMENT-PARITY.md` §7.5 |
| A sign-out that cannot reach the Auth server | `signOut` asks the Auth server to end the session and then deletes the session's cookies whatever it answered. The library alone keeps them when the session's token has expired and that server cannot be reached to renew it — the member would land on the sign-in page still signed in. The session on the Auth server cannot be ended while that server is unreachable: it ends by its own expiry, and no browser holds its tokens | `signOut`, `forgetStaffSessionCookies`; `tests/unit/staff-access.test.ts` ("signing out"); the S1.2 record → "The sealed local run" |
| Open redirect through `next=` | `safeNextPath`: a same-origin path under `/admin` only — no scheme, host, `//`, backslash or control character; decoded once and re-checked; the sign-in pages themselves refused, with or without a query (no loop); fallback `/admin` | `tests/unit/next-path.test.ts`; `tests/e2e/admin-access.anon.spec.ts` |
| A role check only in the browser | None exists: every page and action takes the guard's decision on the server; the enrolment form is the only client module under `/admin` (asserted by a unit test) and imports the two actions alone; the import boundary keeps server modules and both Supabase packages out of client code | `eslint.config.mjs`; `tests/unit/import-boundary.test.ts` |
| Privilege escalation through a stale layout or a panel embedded in another screen | Pages, not layouts, take the guard's decision; actions re-authorise on their own (the prototype's embedded panels did not — `PROJECT-STATUS.md` §10 #8) | every `src/app/admin/**/page.tsx`; `login/actions.ts` |
| A Preview authenticating against PROD | The public and privileged identities must agree on the project; mismatch → unavailable | `cookieClientConfig`; `src/lib/supabase/config.ts` |
| Public sign-up or self-registration | No sign-up call anywhere; the project setting off on TEST (Gate 0 #11) and to be switched off on PROD by the owner (S3.1 / S3.3 at the latest — until then a self-registered PROD account would exist but would not be staff: it has no `staff_profiles` row); users created only by the admin API in the TEST tool or by the owner | Gate 0 #11; `scripts/testing/staff-users.mjs`; `ENVIRONMENT-PARITY.md` §7.5 |
| Secrets in logs or records | No password, code, TOTP secret, QR, token or address is logged; refused passwords are audited by e-mail hash; the QR and the key go to the member's browser once and are never sent back (the confirm step posts the factor's id and the code); a failed audit write logs the action and an error code only; the harness keeps TOTP secrets under the git-ignored `.auth/` and writes no page snapshot when a test fails | the actions; `staff-audit.ts`; `enrol-form.tsx`; `.gitignore`; `playwright.config.ts` |
| Lost history of consequential actions | Each of these writes one insert-only `audit_log` row (actor, action, entity, previous/next, reason): a completed sign-in, a refused password, a refused code, a correct password refused as not staff or revoked, an MFA enrolment, a role change, a revocation, a restoration. The write is **best-effort by design** — a sign-in is not refused because its audit row could not be written — and never silent: a failed insert leaves one server log line with the action and the error code. The revocation and role-change functions have no caller before S2.1 (they are unit-tested against a recording client; the TEST tool performs the same writes); S2.1 treats an access change whose audit row failed as a failed action. | `staff-audit.ts`; `staff-access.ts`; `tests/unit/staff-access.test.ts`; the 0002 record's append-only guards |
| The owner locked out (lost authenticator) | **Recovery route:** the human owner removes the lost TOTP factor in the Supabase dashboard (Authentication → Users → the user → the factor's delete control; the dashboard's exact labels are recorded from the TEST exercise) or, on TEST, runs `pnpm db:test:staff-users --apply --reset-mfa`; at the next sign-in the app forces a fresh enrolment and writes `staff.mfa_enrolled`; no code path skips MFA. The password is changed as part of every recovery (first enrolment is trust on first use — the row above). A second owner account is not planned at launch (D-35), so the dashboard is the route. Exercised on TEST in the S1.2 VS Code leg and recorded in the sprint record. | this file; the 0003 change record → "Recovery route" |
| A revoked member's existing tab | The guard reads the staff row on every request: the next click is denied; the Auth ban prevents a refresh | `decideAccess`; `revokeStaffAccess`; `tests/unit/staff-access.test.ts` |
| A revocation that is lifted again | **Residual risk, by design:** revocation bans the Auth user and deactivates the row; it does not delete the member's sessions (the installed Auth admin client ends a session only with that session's own token; it has no sign-out by user id). While the revocation stands nothing opens. When it is lifted — S2.1's Enable, the TEST tool's `--restore` — every session of that member that has not expired is usable again, a copied cookie included. Procedure: a restoration after a suspected compromise goes with a new password and a factor reset (the member then signs in and enrols afresh); S2.1's Enable is written with this in mind. | `revokeStaffAccess`; the 0003 record → "Revocation" |
| Enrolment abandoned half-way | The start action removes every unverified factor before enrolling a fresh one; an unverified factor never counts as MFA | `login/actions.ts` → `startEnrolment` |
| The QR as an injection vector | The QR is a `data:image/svg+xml` from the Auth server rendered through `<img>` (CSP `img-src 'self' data:`), where SVG cannot run script; it is never inlined as markup | `security-headers.ts`; `enrol-form.tsx` |

## 6. Invariants every Admin merge keeps (for `/close` and the independent review)

1. Every file under `src/app/admin/` that renders protected content or mutates takes the guard's decision before any read or write: `guardAdminPage` in a content page; `getStaffAccess` in the sign-in, verification and enrolment pages and their actions (the same `decideAccess` — they act on the decisions that are not `allowed`); `guardAction` in every action a later sprint adds. The two stated exceptions are `signIn`, which runs before a session exists (the throttle, then the Auth server, then the decision), and `signOut`, which only ends the caller's own session. The proxy decides nothing.
2. No route or action accepts a session below aal2 as a staff session; enrolment needs a staff password session and nothing else (trust on first use — §5).
3. `src/lib/staff/permissions.ts` equals `public.staff_permission_areas()`; a route added to the Admin is added to `ADMIN_ROUTES` with the areas it requires, and nowhere else (a path the table does not know is given the owner-only `settings` requirement by its page, never treated as open).
4. The privileged client is used only after the guard's decision — the one exception is the audit row `signIn` writes for a refused password — and never reads a request cookie or header; `@supabase/ssr` is imported by `src/lib/server/staff-session.ts` only; server-only names are read inside `src/lib/server/` only.
5. Every consequential staff action writes its audit row — best-effort, and a failed write is logged, never dropped silently; from S2.1 on an access change whose audit row failed counts as failed; nothing deletes or updates `audit_log`.
6. Revocation denies on the next request; the recovery route needs no code path that skips MFA.
7. Redirect targets come from `safeNextPath`; no new string is invented inline (docs/content/new-strings.md).
8. The TEST tools refuse a PROD ref before any request; no agent writes to PROD through any channel.
