**Atomic finalization prerequisite — unresolved:** the roadmap says S1.7 has no migration because the columns exist, but requires captured confirmation and `send_confirmation` in one transaction. The current Supabase JS client and migrations contain no finalization transaction primitive. Separate PostgREST requests are separate transactions; ledger/outbox uniqueness alone cannot make their business effects atomic. S1.6 shipped the five checkout RPCs in `0004_checkout`. They create and link a pending order. Inspect their lock order and the caller before specifying the separate captured-payment finalizer. [PostgREST transaction boundary](https://docs.postgrest.org/en/latest/references/transactions.html).

If still missing, present a concrete, minimal additive finalization RPC proposal through the existing server client: contract, locking/retry strategy, forward migration, rollback, access tests and database-change record. Keep default-deny RLS, narrowly scoped `service_role` execution, explicit objects and a pinned search path; prefer invoker privileges where sufficient and never introduce an arbitrary SQL RPC. Obtain the scope decision before those edits; **this draft is not migration approval**. Allocate any filename/number against the then-current ledger and roadmap inventory; D-60 allocated `0004` to the applied `0004_checkout`. All later roadmap numbers are indicative. S1.8 will allocate after S1.7’s actual schema disposition. Do not modify an applied migration or silently renumber future ones.

**Lost-webhook recovery prerequisite — unresolved:** `TECH-ARCHITECTURE.md` §7 requires recovery by API verification as well as signed captured-event confirmation. Reconcile those requirements in an executable recovery contract at Gate 0: verify a supported way to obtain/replay the genuine signed event after API discovery, or obtain an explicit governing-policy/scope decision for another recovery mechanism. API discovery followed by indefinite confirming is not completed recovery. This draft authorises neither a signature bypass nor an unplanned periodic reconciler in S1.8.

Two other verified constraints inform the plan. `provider_events.signature_ok` is immutable and `(provider,event_id)` is unique, so invalid signatures must be rejected before insertion; a false-signature row could permanently block the genuine event. Existing Sentry scrubbers remove queries/fragments but retain URL paths, so the new bearer-token path needs redaction. The dynamic order page also inherits the known server-rendered 404 issue; the catalogue's static-slug workaround cannot enumerate private order tokens.

### H.3 Step 1 — the contracts

*Amended 2026-11-26 after the independent review's round 1 (H.14; `docs/database-changes/S1.7-0006-payment-evidence.md`): the provider check takes every live payment Razorpay lists with its observed amount and currency — more than one, or other money, is a review no capture clears; a repeated signed event whose money contradicts the stored payment is a review; a checkout reload or the order page never offers payment beside a review with money on record, and asks Razorpay read-only when the database shows none; the checkout never ends a hold on its own clock; a relaunch and the order page's retry need the order still awaiting payment; the ledger keeps the exact verified bytes. Where a rule below says otherwise, H.14 and the 0006 record govern.*

**Authority.** Only a signature-verified `payment.captured` event, matched to the stored purchase, confirms an order. The Checkout return can only record that a payment was *reported*; Razorpay's API can only *hold* an order. Neither marks anything paid (D-68).

**Two secrets, two signatures.** The Checkout return: `HMAC-SHA256("<provider order id>|<payment id>", RAZORPAY_KEY_SECRET)`, where the order id is the one the server stored for the caller's own attempt — the browser's copy is never read. The webhook: `HMAC-SHA256(raw request bytes, RAZORPAY_WEBHOOK_SECRET)` from `X-Razorpay-Signature`, over the bytes as received, before anything is parsed; parsed JSON is never re-serialised to recreate signed bytes. Both: shape checked first (64 lowercase hex), then a constant-time comparison of equal-length buffers (`src/lib/server/payments/signature.ts`).

**Payment gate.** `paymentsGate()` (`src/lib/server/payments/config.ts`) is the deployment's provider half alone: not Production; the server's identity resolved to the TEST project; a Razorpay Test Mode key with its secret; the webhook secret; the order-link secret. It does not read `SALES_MODE`, Turnstile, Upstash or the business rule — those decide whether a *new* order may start. `salesGate()` now stands on the same provider half plus its own conditions, so **checkout does not open without `RAZORPAY_WEBHOOK_SECRET`**: an order must not be payable where its payment could not be confirmed.

**The webhook** (`POST /api/webhooks/razorpay`, Node.js runtime, never cached), in this order: POST only (`405`, `Allow: POST`) → payment gate (`503 unavailable`) → the signature header's shape (`400 invalid_signature`) → a bounded read of at most 256 KiB (`413 too_large`) → the HMAC (`400 invalid_signature`) → UTF-8 JSON and the event envelope (`400 invalid_payload`) → the privileged client (`503`) → **the ledger** (`payment_record_event`; a refused shape `400`, anything else `503`) → a row already processed or ignored is acknowledged without another call → **the effect** (`payment_process_event`; any refusal `503`) → `200 {"status":"ok"}`. Nothing is inserted before the signature has verified. A `5xx` asks Razorpay to retry; a `2xx` is given only after the event's effect has committed or was already there. No answer and no log line carries anything of the request: logs are fixed text with enumerated codes.

**Event identity.** The ledger id is the `x-razorpay-event-id` header, or `sha256:<hex of the raw body>` when the header is absent or not of the accepted shape. The same id with other content is kept beside the first under a derived id and processed (the change record, contract 2).

**The database's part** is the change record's contracts 1–16 (`docs/database-changes/S1.7-0005-payment-finalization.md`): ledger first; one event, one effect, one transaction; only `payment.captured` confirms and only an eligible order; one unit of pending work per order; everything else recorded and flagged; forward-only payment rows; the lock order.

**State transitions** (the payment's own row · the order):

| Event or call | Payment row | Order |
|---|---|---|
| Verified Checkout return | `created`, `signature_verified` (once) | unchanged — "a payment is reported" |
| `payment.authorized`, right order and amount, nothing in the way | `authorized` | `needs_review`, hold `authorized_only` |
| `payment.captured`, eligible (contract 4) | `captured` | `captured` / `confirmed`, `confirmed_at`, items stage 0 → 1, flag and hold cleared, one audit row, one `send_confirmation` |
| `payment.captured` for an order already captured, or with another live payment | `captured` | review `extra_payment` |
| Wrong amount / wrong currency | amount kept on the row / no row | review `amount_mismatch` / `currency_mismatch` |
| Capture stored after `expires_at`, or the order has none | `captured` | review `late_capture` / `expiry_missing` — never confirmed, never refunded |
| Capture for an order no longer awaiting payment | `captured` | review `order_not_payable` — never brought back |
| Valid capture for an order under a review that is not a hold | `captured` | review `order_under_review` — a person decides |
| `payment.failed` | `failed` | unchanged — recoverable while the deadline stands |
| An older or repeated event | unchanged | unchanged (`duplicate_capture`, `stale_authorized`, `stale_failed`) |
| Reference no checkout row holds | no row | no order touched; audit row tied to the ledger row |
| API shows a captured / authorised payment (provider check) | no row | hold `capture_unverified` / `authorized_only`, only on an order awaiting payment under no other review |

**Retry ownership — when may a payment be started again?** A first launch of an untouched provider order asks nothing more than S1.6 did. Before **any later launch** of the same order (a reload, a second press, another tab) — and, since H.8, before an order past its deadline is called "expired" — the server asks Razorpay which payments that order has (`GET /v1/orders/:id/payments`, 5-second limit, no redirect, validated answer, at most one page of 100): *clear* (none, or only failed ones) → the payment window may open again (past the deadline: "the time to pay has passed"), **unless a payment reported by a verified Checkout return stands on record for the order — then "being confirmed", never a launch**; *captured* or *authorised* → the hold is recorded and the customer sees "being confirmed", with no pay button; *in flight* (a `created` payment) or *unavailable* (timeout, error, an answer that does not validate) → "could not be checked … do not pay again", with no pay button. An order that is confirmed, held or under review is never payable. Uncertainty never starts a payment. On the page itself (H.8): once a window has been opened for an order, its deadline, a re-open and any answer that cannot be had all go through the server — the page never decides "the time has passed" or "Nothing was charged" on its own clock; and a reload whose question about the stored attempt cannot be answered offers no new payment.

**Lost webhook (D-68).** The signed event stays the only authority. Recovery, in order: Razorpay's own retries for 24 hours; the owner's **Replay events** in the Razorpay Dashboard (unacknowledged events, up to 7 days; older through Razorpay Support). What the application adds is the *persisted, visible* escalation: when the customer returns, reloads or the order page asks (bounded), the provider check finds the captured payment, raises `capture_unverified` with an audit row, and the page says the payment is being confirmed — until the replayed event arrives. **What that event does depends on when it is stored (D-20, found in H.8):** stored before the order's deadline it confirms the order and clears the hold; stored after it — which every replay made after Razorpay's retries have run out is — it ends as `review:late_capture`, a persisted, audited review that a person resolves (the Admin's queue is S2.2; no order is confirmed or refunded by any function before then). So the recovery completes automatically only within the payment window; after it, it is a bounded escalation to a person, not a confirmation. Whether evidence recorded in time should let a late-stored signed capture confirm was open as **D-69** — decided by the owner on 2026-11-23: kept as built (H.10; `PROJECT-STATUS.md` §8a). No scheduled reconciler exists and none is assigned to S1.8. Surfacing held and flagged orders to staff is the Admin's (S1.9 / S2.2).

**The return flow.** Razorpay's window reports to the page → the page says "not confirmed yet" (NS-05) → it posts exactly the payment id and the signature with its attempt key to `verifyCheckoutReturnAction` → the server: payment gate, strict parse, rate limit (`resume` bucket), the attempt by its key's hash, the 24-hour window S1.6 honours, a linked provider order, the signature against the **stored** order id → `payment_return_state(hash, payment id)` records the payment as reported → the order's link is derived from its salt and checked against its stored hash → the browser is sent to `/order/<token>` — the only navigation, and only to a path of exactly that shape. A rejected, throttled or unavailable answer leaves the customer on the checkout with its line; the page retries the verification twice, two seconds apart.

**The order link (D-09 as amended by D-61).** `/order/<token>`: 43 base64url characters. The server hashes the presented token, reads the order by that hash through `order_confirmation_view` only, and re-checks the stored hash in constant time. The token is never stored, logged or put in metadata. The server hands the link only to the browser that presents the order's own attempt key, and only once a verified payment signal exists for that order — a Checkout return whose signature verified, or a signed provider event (a hold raised from the API alone yields no link). From S1.8 the confirmation email carries it too.

**The page's state — from the database only** (`orderPageState`, `src/lib/schemas/order-confirmation.ts`): *confirmed* (the order is captured) · *confirming — payment* (a payment is reported, authorised or captured and the order is not confirmed yet, **or the order carries a hold its own capture clears** — since H.8) · *confirming — review* (flagged without a hold, or no deadline) · *failed — retry* (pending, no payment known, the deadline ahead) · *failed — closed* (the deadline passed, or the order no longer awaits payment). A confirmed state is final for the page: a later answer never replaces it.

**Privacy of the address.** `/order/*` answers `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and its own `X-Robots-Tag: noindex, nofollow`; the page is rendered per request; the token is redacted to `/order/[token]` in everything Sentry sends from the browser and the server (H.6). Since H.8: the checkout never loads a provider's script into a document that was opened at an order link (it loads itself again first), because a third-party script could read that address from the page's navigation and resource records — that guard is the protection, since the shell's links and the order rows' artwork links are client navigations; the order page's own action and help links are full page loads besides. Not removable: Vercel's own request log holds every path, as for any site on the platform — it is visible to project members only and is never shared as evidence (`docs/THREAT-MODEL.md`).

**S1.8 hand-off.** The outbox row: kind `send_confirmation`, entity `order` / the order's id, dedupe key `send_confirmation:order:<order id>`, payload `{"v": 1}` — no token and no personal data. The worker reads the order by id, derives the link at send time from `confirmation_token_salt` and `ORDER_TOKEN_SECRET` and checks it against `confirmation_token_hash` (`src/lib/server/checkout/tokens.ts`). The expiry job treats `expires_at` exactly as the finalizer does (the database's clock; a linked order with no deadline is unresolved, never unlimited) and must set `payment_hold = NULL` in the same UPDATE as any review it raises. A held order (`capture_unverified`, `authorized_only`) **and an order with a payment reported by a verified return** must not be expired as unpaid without a person or a provider answer — `orderPageState` reads a non-pending order as "the time to pay has passed" before it looks at the payments, so an order expired with a reported payment on record would say so to a customer who may have paid (the builder's review, H.8). Before expiring, the job asks the provider as the checkout does (`src/lib/server/payments/reconcile.ts`). Two more for S1.8 to weigh with the expiry job: D-69 (a late-stored signed capture with evidence recorded in time); and Razorpay Checkout's own `timeout` option, which the window does not set — set to the time left before the deadline it would stop most payments that can only end as `late_capture`. S1.8's migration is `0006`.
