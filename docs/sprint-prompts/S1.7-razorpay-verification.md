## A. Diagnosis and readiness

S1.7 makes a verified captured payment produce one durable confirmation and one queued confirmation task. The browser callback can only lead to an honest confirming state; the order page reads its state from the database.

This is **not** S1.7's future merge-base or reviewed head. The roadmap/status trackers retain a pre-merge S1.4 snapshot; their closure reconciliation remains S1.5's step 0. Current source has the catalogue, public shell and staff authentication, migrations `0000`–`0003`, order schemas and schema-level integration tests. **S1.5 and S1.6 are prepared prompts, not implemented dependencies.** No bag/checkout runtime, Razorpay callback/webhook, payment finalizer, `/order/[token]` route or worker exists yet.

**Atomic finalization prerequisite — unresolved:** the roadmap says S1.7 has no migration because the columns exist, but requires captured confirmation and `send_confirmation` in one transaction. The current Supabase JS client and migrations contain no finalization transaction primitive. Separate PostgREST requests are separate transactions; ledger/outbox uniqueness alone cannot make their business effects atomic. S1.6 has its own unresolved checkout transaction prerequisite; even a future checkout RPC would not prove that payment finalization exists. Recheck the actual S1.6 implementation before deciding what is needed. [PostgREST transaction boundary](https://docs.postgrest.org/en/latest/references/transactions.html).

If still missing, present a concrete, minimal additive finalization RPC proposal through the existing server client: contract, locking/retry strategy, forward migration, rollback, access tests and database-change record. Keep default-deny RLS, narrowly scoped `service_role` execution, explicit objects and a pinned search path; prefer invoker privileges where sufficient and never introduce an arbitrary SQL RPC. Obtain the scope decision before those edits; **this draft is not migration approval**. Allocate any filename/number against the then-current ledger and roadmap inventory; `0004_messages` is currently reserved for S1.8. Do not modify an applied migration or silently renumber future ones.

**Lost-webhook recovery prerequisite — unresolved:** `TECH-ARCHITECTURE.md` §7 requires recovery by API verification as well as signed captured-event confirmation. Reconcile those requirements in an executable recovery contract at Gate 0: verify a supported way to obtain/replay the genuine signed event after API discovery, or obtain an explicit governing-policy/scope decision for another recovery mechanism. API discovery followed by indefinite confirming is not completed recovery. This draft authorises neither a signature bypass nor an unplanned periodic reconciler in S1.8.

Two other verified constraints inform the plan. `provider_events.signature_ok` is immutable and `(provider,event_id)` is unique, so invalid signatures must be rejected before insertion; a false-signature row could permanently block the genuine event. Existing Sentry scrubbers remove queries/fragments but retain URL paths, so the new bearer-token path needs redaction. The dynamic order page also inherits the known server-rendered 404 issue; the catalogue's static-slug workaround cannot enumerate private order tokens.
