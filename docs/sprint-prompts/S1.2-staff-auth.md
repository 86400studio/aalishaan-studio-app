## A. Diagnosis

S1.1 is Done: the tables that cannot change after the first real order exist on TEST and PROD, among them `staff_profiles` with the role enum `owner_admin` / `operations` / `support` and the insert-only `audit_log` — and no row in either, because no staff user exists yet. S1.2 puts the access control in front of everything the Admin will ever show: a Supabase Auth session held in cookies and re-verified on the server on every `/admin` request, mandatory TOTP MFA, a role read from `staff_profiles` on every request and evaluated through the six permission areas of the final Admin (D-35), a login throttle that fails closed, audit rows for every consequential auth event, and a revocation path that stops a session within one request. It comes before any page (`ROADMAP.md` → Ordering rationale) so that the prototype's browser-side role checks are never ported (D-32e) and so that S1.9's Admin lands behind a guard that is already reviewed.

The owner requested one branch/PR per sprint: this record, the implementation and the pre-review bookkeeping travel together; the Codex brief is delivered after the tested candidate exists. Merge/smoke facts go to the merged PR; the next sprint's step 0 reconciles them.

## B. Goal and scope

Implement ROADMAP S1.2 exactly: Supabase Auth email + password for staff only, with no public sign-up anywhere in the app; mandatory TOTP MFA (an account without a verified factor is forced to enrol before it can see anything; a session below `aal2` is never a staff session); one server guard used by every `/admin` page, server action and future route handler, download and export; the roles `owner_admin`, `operations`, `support` mirrored in the database through the additive `0003_staff_auth` (the MFA and revocation columns of `staff_profiles`, the `permission_area` enum, the role → area function, an own-row SELECT policy for `authenticated` at `aal2`) and evaluated on the server through the six areas (work, support, finance, catalogue, settings, export — owner all six, Operations work + catalogue, Customer support support); section access as the final Admin's `isAllowed` shows it (`TECH-ARCHITECTURE.md` §5); Upstash login throttling by hashed e-mail and hashed client address, failing closed; session revocation (the profile's `active` flag with `revoked_at`, plus an Auth ban that stops token refresh); audit rows for sign-in, failed sign-in, MFA enrolment, role change and revocation; the owner recovery route documented (exercised on TEST in the VS Code leg); `docs/THREAT-MODEL.md`; the three TEST staff users through a bounded tool and the Playwright auth-setup project; allowed and denied tests per role; a blank protected `/admin` shell with one owner-only section (`/admin/staff` — Staff & Access, `settings`) and one finance route (`/admin/support?view=refunds` — Support › Refunds, `finance`) so the acceptance denials are real routes, each rendering only the honest "arrives in sprint" state (NS-10) and no data.
