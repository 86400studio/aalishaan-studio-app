## A. Diagnosis and readiness

S1.6 turns the S1.5 bag into a durable pending order before opening Razorpay Checkout in Test Mode. At preparation, S1.4 is merged, **S1.5 is only planned**, and no checkout, bag implementation, Turnstile verifier or Razorpay integration exists in `src/`. Recheck those facts at execution; do not copy an assumed S1.5 API into production code.

**Transaction prerequisite — unresolved:** the roadmap says S1.6 has no migration, but requires customer/address, order, items, snapshot and payment attempt in one transaction. The installed runtime has Supabase JS, no direct Postgres driver, and migrations `0000`–`0003` contain no checkout transaction RPC. The S1.1 integration tests insert individual rows; they are not a checkout transaction implementation. PostgREST transactions are per request, so separate `.insert()` requests cannot satisfy this invariant. See [PostgREST transactions](https://docs.postgrest.org/en/latest/references/transactions.html).

Recommended resolution for the owner before dependent implementation: approve an additive, narrowly privileged checkout transaction RPC through the existing server Supabase client, with a forward migration, paired rollback, access tests and database-change record. Keep existing table grants/default-deny RLS, use explicit objects and a pinned search path, revoke public/anon/authenticated execution, and prefer invoker privileges sufficient for `service_role`. Do not introduce a general SQL execution RPC. The durable retry/concurrency design must be settled at the same time. **This recommendation is not approval to write or apply a migration.** Recheck whether intervening authorised work has already supplied the primitive; otherwise present the exact proposed files and contract before approval. Allocate a migration number against the then-current ledger and planned inventory; `0004_messages` is already reserved for S1.8 in the roadmap, so do not silently reuse or renumber it.

**Confirmation-capability lifecycle prerequisite — unresolved:** D-09 requires a random capability stored only as a hash. This draft also requires recovery after a lost response/reload without replacing that hash, while S1.7 owns the route and S1.8 owns email delivery. A hash cannot recover the original random token. Before issuance code, settle a concrete feasible lifecycle covering initial delivery, ownership-bound resumption, S1.7's return link and S1.8's future email link. If D-09's constraints need a change or another secret/transport, present the exact governing decision and allowed-file amendment; do not silently store a raw token in database/outbox/browser storage, expose a discovery API or rotate the customer's capability. Email implementation stays S1.8, but issuance feasibility cannot be deferred until after S1.6 freezes it.

Two other readiness facts matter: the existing rule seed is closed and its shipping/tax fields are unknown; Preview needs an explicitly authorised synthetic rule/test calculation policy before a test order can be created. Production's initial closed rule is a human-only prerequisite documented in `docs/database-changes/S1.1-0002-orders.md`, not permission for the builder to write PROD.

### H.3 Step 1 — proposed contracts (two independent designs, three adversarial critiques, one synthesis)

**Sales gate (no network, first in every action):** open only when `SALES_MODE === "test"`, the deployment context is not `production`, the server identity resolves to the TEST project, the public Razorpay key is a Test Mode key, and every needed secret is present. Anything else — Production, `off`, `live`, unknown context, a mismatched identity, a missing name — answers closed (NS-04) with zero business writes and zero calls to Upstash, Turnstile or Razorpay. The database function re-checks the effective rule (`sales_open`, `synthetic`) inside its transaction.

**Order of work for a submission:** gate → strict bounded parse and normalisation (all checkout fields required; mobile normalised to ten digits; PIN shape; quantities 1–99) → rate limit (own namespace, fail closed) → Turnstile on every submit (fail closed; dummy keys accepted only outside Production, where hostname/action cannot be checked) → the atomic write → the provider step. A resume (attempt key only) passes the gate and its own rate limit, needs no Turnstile, and creates no business row.

**Migration `0004_checkout` (additive; paired down file; change record):**

- `orders`: `checkout_attempt_hash` (unique), `checkout_payload_mac`, `confirmation_token_salt` — all nullable, shape-checked.
- `payment_attempts`: `provider_order_state` (nullable: `intent` / `requested` / `linked` / `failed` / `unknown`; NULL on rows that are not a checkout's order-creation row, so S1.7 stays free to add per-payment rows), `provider_create_requested_at`, `provider_order_created_at`; unique `(provider, provider_order_id)` and unique `(order_id)`, both only where `provider_order_state` is not null.
- Two guard triggers: the token hash, salt, attempt hash, payload MAC and a set `expires_at` never change; a checkout attempt row's order, amount, currency, provider order id and provider creation time never change, and its state moves only `intent → requested → linked | failed | unknown` and `unknown → linked | failed`.
- Five functions, house style (`plpgsql`, `set search_path = ''`, never `SECURITY DEFINER`, EXECUTE revoked from `public`, `anon`, `authenticated` and granted to `service_role` only), no table grant changed, no generic SQL entry point:
  - `checkout_create_pending_order(p_request jsonb)` — the atomic write, or a replay;
  - `checkout_attempt_state(p_attempt_hash text)` — the one read path; returns no personal data and no ids beyond what a launch needs;
  - `checkout_claim_provider_create(p_payment_attempt_id uuid)` — one `UPDATE … WHERE state = 'intent'`; re-checks the rule and how old the order is;
  - `checkout_link_provider_order(p_payment_attempt_id uuid, p_provider_order_id text, p_provider_created_at timestamptz)` — provider id, provider creation time and `orders.expires_at` in one transaction; idempotent for the same id;
  - `checkout_close_provider_create(p_payment_attempt_id uuid, p_outcome text, p_reason text, p_needs_review boolean)` — `requested → failed | unknown`, with an audit row.
- Not added: an attempts table, any raw or encrypted token, new values in `orders.payment_status` or `payment_attempts.status`, an outbox row, stock or reservation fields.

**The atomic write, in order:** validate structure and every value shape with fixed-message custom codes (so no table CHECK ever echoes a customer's row into an error or a log) → advisory lock on the attempt hash → replay lookup (same hash and same MAC returns the existing order without touching the number counter; a different MAC is refused) → the effective rule (`effective_from <= now()`, latest first, version as tie-break; closed, missing or wrong `synthetic` refuses) → charges (unknown shipping/tax stay NULL; a real rule with unknown charges or an exclusive tax without a rate refuses) → the bought variants and their artworks read and locked for the transaction (unknown, not Active or not `made_to_order` refuses) → the recomputed total compared with the total the page showed (a precondition that can only refuse) → the seven current policy versions → plain INSERTs: contact, address, order (the 0002 trigger assigns the number; never ON CONFLICT), snapshot, payment attempt (`intent`), items last. Any failure rolls everything back, the number included. The snapshot carries items, totals, address, rule and policy references — not the email or phone.

**Attempt ownership:** the browser mints a 32-byte random attempt key when the customer first presses pay; the server stores only its SHA-256. The payload is bound by an HMAC keyed with the attempt key (no digest of personal data sits on `orders`). Presenting the key is the only way to reach an attempt — no lookup by email, phone, order number or id exists. Two guests with the same email or phone get two contacts, two addresses and two orders. A key read back from storage may only resume, never submit (so a planted key cannot capture a later order); the server honours a key for 24 hours from `placed_at`.

**Provider step:** exactly one Razorpay create call per attempt, ever — the claim is a single compare-and-set. Receipt `pa_<payment attempt id>`; notes carry the order number only. A good answer (id, amount, currency and receipt all matching the stored intent) is linked with its original `created_at`; the deadline is that time plus the pinned rule's minutes and is never extended. A definite refusal is `failed` (the customer starts again as a new order). A timeout, 5xx, "duplicate request" or "operation in progress" is `unknown`: held, never re-created, recovered only by a bounded read by receipt (exactly one exact match links; none or several stay held). `needs_review` is set only for an ambiguous or mismatched provider answer, a link conflict or a configuration rejection. Launch data reaches the browser only for a linked, pending, unexpired order. While such an order exists the customer cannot start another from that attempt. Browser callbacks, failures and dismissals call nothing that changes state and never empty the bag; a success callback shows only the unverified NS-05 state.

**Confirmation capability (needs a D-09 amendment — H.4 #2):** `salt = 32 random bytes` per order; `token = base64url(HMAC-SHA-256(ORDER_TOKEN_SECRET, label + salt))`; the database stores the salt and the token's SHA-256, never the token. The token can therefore be re-derived for S1.7's verified return and S1.8's email without rotation or storage; `/order/[token]` verifies by hash and needs no secret. S1.6 issues it (salt and hash commit with the order, set once) and proves re-derivation in tests, but **does not hand it to the browser**: nothing in S1.6 consumes it, and S1.7 delivers it only after its signature check. Honest cost, to be stated in the amendment: someone holding both a database copy and the secret could derive every order's link, and rotating the secret revokes none (verification uses the stored hash); a re-issue runbook goes in the change record.
