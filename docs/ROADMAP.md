# ROADMAP.md — Build Order

The scope and dependency plan for **Aalishaan Studio** V1: the approved public storefront (prototype E8, public design locked at R13 + mobile M1–M5) rebuilt as a real store, plus the Admin built to the final Admin design — **Admin A2 — 86400 UI edition** at `prototype/admin/` (D-PRE-23; "the final Admin"; local prototype revision E10 = public E8 + the final Admin + the three additions of 2026-09-23, D-36–D-39). AF1 (`prototype/docs/ADMIN-FINAL-FEATURES.md`: 26 capabilities O1–O9, C1–C2, P1–P4, S1–S3, R1–R2, G1–G6; acceptance stories US01–US23) stays the canonical capability and story scope, and `prototype/admin/CAPABILITY-MAP.md` maps every capability ID to its home in the final Admin; AF1 §3's menu layout is superseded by D-PRE-23, its capabilities and stories are not. The final Admin has seven sections in this order — Orders (landing page), Customers, Products, Support, Reports, Staff & Access, Connections — an owner menu (Store setup, Access & backups) and a top bar (global search, View website, Help & demo); its prototype-only mechanisms are replaced, never ported (D-32). Delivery decisions D-01–D-39 are in `PROJECT-STATUS.md` §8a (D-28–D-36 are the consequences of the final Admin; D-37–D-39 are the three additions approved on 2026-09-23 — the order-intake pause and waiting list, the online-only payment policy, and the refund entry point on the Payment stage — built into prototype E10 as sample behaviour). `PROJECT-STATUS.md` records current state; `WORKFLOW.md` records how work ships; `APPROVED-INPUTS.md` says where the approved copy, design and data live.

**Primary conversion:** a completed guest purchase paid through Razorpay that produces a durable, server-verified order the studio can see and the customer can track.

**Shape of the plan:** 37 sprints — 3 Setup, 9 Stage 0, 21 Stage 1, 4 Launch — normally one reviewable PR each. One sprint at a time. Where a brief says so (S0.1, S0.2, S1.9, S2.5) a sprint may land as two PRs `a`/`b` in sequence; S3.1 (owner-input PRs) and S3.2 (parent run plus numbered fix PRs `S3.2-Fn`) are multi-PR by design. Every PR is recorded in the `PROJECT-STATUS.md` §2 Notes column (decision D-25). Every sprint brief below is the seed for its `/sprint-prompt` record; the prompt may narrow a brief, never widen it. IDs are stable; a brief that must be split at prompt time becomes `S2.9a`/`S2.9b`, never a renumbering.

## Ordering rationale

Setup comes first because the SOP forbids product work without a protected repo, Code Check and an isolated Preview (`WORKFLOW.md`, `TECHNICAL-INTEGRITY.md`). Stage 0 puts schema (S1.1) and staff access control (S1.2) before any page so that identities, the paise money model, the provider-event ledger and the audit log — the things that cannot be changed after the first real order — exist before anything writes to them, and so the prototype's browser-side role checks (its hidden role select, role preview and sample sign-in — D-32e) are never ported. Public pages follow in dependency order (shell → browse → artwork/bag → checkout → payment → worker/email → Admin/Track) so that each PR stays reviewable and the first real Test Mode sale happens as early as it can safely happen. Stage 1 follows AF1 §8 exactly, with three grafts from the judged alternatives: the failure queue and pause controls land with the Orders attention and follow-up model (S2.2 — the final Admin has no Today screen, D-28) because readiness automation must not run before an owned failure queue exists; the refund engine lands early (S2.4) because money-out bugs are the hardest to retrofit; and Shiprocket, invoices/settlements and imports/exports are each split so a reviewer reads one idempotency story per PR. The Admin is built section by section to the final Admin (Admin A2 — 86400 UI edition, D-PRE-23): S1.9 lays the seven-section shell with Orders as the landing page, S2.1 fills the owner's Store setup, Staff & Access and Connections, and each later slice fills the stage panel, tab or tool of the final Admin that `prototype/admin/CAPABILITY-MAP.md` names as its capability's home — never a prototype-only mechanism (D-32). Launch applies the owner's commercial inputs (S3.1) **before** the whole-site suite (S3.2) so the gate exercises real rules, connects live providers only after the gate is green and while sales stay closed (S3.3), and opens sales as the last reviewed change (S3.4). S2.21 closes Stage 1 because it composes foundations laid earlier — the S1.6 sales gate (which carries the `capacity` reason from the start so the pause needs no later schema change), the S2.12 consent model, the S2.18 outbox templates and the S2.19 Operations view — instead of adding new ones (D-37); the Payment-stage refund entry point rides the S2.4 refund engine (D-39). Decision IDs: D-01–D-39 in `PROJECT-STATUS.md` §8a.
