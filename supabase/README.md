## Layout

| Path | Purpose |
|---|---|
| `migrations/NNNN_name.sql` | Forward migrations, applied in version order. `0000_init.sql` is the S0.2 baseline; `0001_catalogue.sql` and `0002_orders.sql` are S1.1 (drafted 2026-10-05; pending the TEST apply — their records in `docs/database-changes/`). The CLI's file pattern is `^([0-9]+)_(.*)\.sql$` (verified in its source at 2.117.0), so the roadmap's four-digit versions are discovered as written; only a 14-digit `<timestamp>_init.sql` older than `20211209000000` would be skipped as a legacy dashboard file. |
| `rollbacks/NNNN_name.down.sql` | The paired schema-recovery artifact of each forward file — **outside `migrations/`**, so `db push` can never run it. A down file reverses schema; it does not restore data and it is never run because it exists. |
| `config.toml` | The CLI's project configuration (generated by `supabase init` 2.117.0; `project_id` set, seeding disabled). Local Docker development is not used in this project. |
| `.gitignore` | The CLI's own: `.branches/`, `.temp/` (where `link` keeps the linked ref). Nothing under `supabase/` holds a value. |

## What the CLI does when it applies a file

Each forward file is sent as **one pipelined batch that ends with the ledger insert** into
`supabase_migrations.schema_migrations (version, name, statements)` — for `0000_init.sql` the version is
`0000` and the name `init`. The extended protocol runs a pipeline as one implicit transaction, so a failing
statement rolls back the file and its ledger row together (statements that cannot run inside a
transaction, such as `CREATE INDEX CONCURRENTLY`, are executed on their own — the baseline has none). The
dashboard SQL editor runs a pasted script as one implicit transaction too, but it writes no ledger row.

## Commands (names only — the CLI prompts for or reads secrets itself; never paste one)

Authentication: `pnpm exec supabase login` once (browser flow; the access token goes to the OS credential
store) or `SUPABASE_ACCESS_TOKEN` in the trusted process. The database password is prompted for by
`link`/`push` and saved in the OS credential store, or supplied through `SUPABASE_DB_PASSWORD`.

```bash
pnpm exec supabase --version                                  # 2.118.0
pnpm exec supabase link --project-ref <TEST_REF>              # once per machine; writes supabase/.temp/
pnpm exec supabase migration list --linked                    # local files vs the remote ledger
pnpm exec supabase db push --linked --dry-run                 # prints what would be applied; applies nothing
pnpm exec supabase db push --linked                           # TEST apply — only under the owner's explicit authorisation
pnpm exec supabase db dump --linked --schema public -f <scratch>/test-schema.sql   # read-only schema capture for P8
```

`--project-ref <REF>` on `db push` / `migration list` targets a project without re-linking; the human PROD
procedure uses it explicitly (`docs/database-changes/S0.2-0000-init.md`). Never run `db reset` against a
linked remote project, never `--include-seed` (seeding is disabled in `config.toml` as well), never a down
file through `db push`.

## S1.1 data tools (TEST only — every one a dry run without `--apply`)

```bash
pnpm db:test:seed                                              # the catalogue plan vs TEST: 22 artworks, 66 variants, 330 image rows, 7 policy versions, business_rules v1
pnpm db:test:seed --apply                                      # writes missing rows; a differing row is reported, not overwritten (--overwrite applies the plan, referenced variants kept)
pnpm db:test:upload-catalogue --source-root <checkout of b24dce1b…>          # verifies the pinned checkout and every enumerated WebP by SHA-256
pnpm db:test:upload-catalogue --source-root <checkout of b24dce1b…> --apply  # uploads 330 objects to the public bucket catalogue-public (idempotent)
pnpm db:test:reset --namespace=catalogue:                      # deletes only the seeded catalogue rows, refused while an order references a variant
pnpm db:test:reset                                             # the S0.2 form: synthetic system_checks rows of one namespace (fixture: / integration:)
```

## Recovery

Prefer forward fixes: every planned migration is additive. When a schema rollback is unavoidable, a human
runs the paired `rollbacks/*.down.sql` by hand after the checks in the change record, on TEST first (for S1.1,
`0002_orders.down.sql` before `0001_catalogue.down.sql` — `order_items` references the catalogue), then
records the reversal in the ledger with `supabase migration repair --status reverted <version>`. Host
rollback (Vercel Instant Rollback) never touches the database.
