# supabase/ — migrations, rollback artifacts and CLI usage

Supabase CLI **2.118.0** since 2026-10-02 (PR #16, which carried the Dependabot commit of the closed PR #11 of 2026-10-01; 2.117.0 at S0.2; `pnpm exec supabase`, a devDependency; the platform binary is an optional package,
nothing is downloaded at install). Two owner-held projects: **TEST** `aalishaan-studio-test` (Local and
Preview) and **PROD** `aalishaan-studio-prod` (Production); refs by name in `docs/PROJECT-STATUS.md` §9.
Rules: `docs/WORKFLOW.md` → Database change protocol, `docs/SUPABASE-VERCEL-SETUP.md` Part B,
`docs/SUPABASE-MCP-SAFETY.md` (Profile B since D-40, 2026-09-25: `supabase-dev` on TEST; `supabase-prod-readonly`
may only verify — no agent writes to PROD through any channel). One record per change in
`docs/database-changes/`.

## Layout

| Path | Purpose |
|---|---|
| `migrations/NNNN_name.sql` | Forward migrations, applied in version order. `0000_init.sql` is the S0.2 baseline; `0001_catalogue.sql` and `0002_orders.sql` are S1.1 (drafted 2026-10-05, corrected, applied to TEST and the rollback rehearsed there on 2026-10-06; PROD waits for the owner's own apply — their records in `docs/database-changes/`). The CLI's file pattern is `^([0-9]+)_(.*)\.sql$` (verified in its source at 2.117.0), so the roadmap's four-digit versions are discovered as written; only a 14-digit `<timestamp>_init.sql` older than `20211209000000` would be skipped as a legacy dashboard file. |
| `rollbacks/NNNN_name.down.sql` | The paired schema-recovery artifact of each forward file — **outside `migrations/`**, so `db push` can never run it. A down file reverses schema; it does not restore data and it is never run because it exists. |
| `config.toml` | The CLI's project configuration (generated by `supabase init` 2.117.0; `project_id` set, seeding disabled). Local Docker development is not used in this project. |
| `.gitignore` | The CLI's own: `.branches/`, `.temp/` (where `link` keeps the linked ref). Nothing under `supabase/` holds a value. |

## What the CLI does when it applies a file

Each forward file is sent as **one pipelined batch that ends with the ledger insert** into
`supabase_migrations.schema_migrations (version, name, statements)` — for `0000_init.sql` the version is
`0000` and the name `init`. The extended protocol runs a pipeline as one implicit transaction, so a failing
statement rolls back the file and its ledger row together (statements that cannot run inside a
transaction, such as `CREATE INDEX CONCURRENTLY`, are executed on their own — the baseline has none). The
dashboard SQL editor runs a pasted script as one implicit transaction too, but it writes no ledger row.

## Commands (names only — the CLI prompts for or reads secrets itself; never paste one)

Authentication: `pnpm exec supabase login` once (browser flow; the access token goes to the OS credential
store) or `SUPABASE_ACCESS_TOKEN` in the trusted process. At 2.118.0 `link` neither asks for nor stores a
database password; `migration list`, `db push` and `migration repair` take one only from `--password` or
`SUPABASE_DB_PASSWORD`, and without one they sign in with the access token and create a temporary login role
on the project named on the command ("Initialising login role…"). `db query` has no `--password` flag; on
2026-10-06 `db query --linked --project-ref <TEST_REF>` printed the same "Initialising login role…" and
reached TEST. **The token is account-wide, so the project
ref on each command is the only thing that separates TEST from PROD** (S1.1, 2026-10-06 — the 0001 record).

```bash
pnpm exec supabase --version                                  # 2.118.0
pnpm exec supabase link --project-ref <TEST_REF>              # once per checkout, by the owner in their own terminal; writes supabase/.temp/project-ref
cat supabase/.temp/project-ref                                # read the link back: it must print the TEST ref
pnpm exec supabase migration list --project-ref <TEST_REF>    # local files vs the remote ledger
pnpm exec supabase db push --project-ref <TEST_REF> --dry-run # prints what would be applied; applies nothing
pnpm exec supabase db push --project-ref <TEST_REF> --yes     # TEST apply — only under the owner's explicit authorisation (--yes: the builder's process has no terminal)
pnpm exec supabase db dump --project-ref <TEST_REF> --schema public -f <scratch>/test-schema.sql   # schema capture for P8 (needs Docker; S1.1 uses the catalog query of the 0001 record instead)
pnpm exec supabase db query --linked --project-ref <TEST_REF> --file supabase/rollbacks/<file>     # a down file on TEST — only under the owner's written authorisation naming the file and the project ("Recovery" below)
```

Name the project on every command that reaches a database (S1.1, 2026-10-06): `--project-ref <REF>` is
accepted by `db push`, `migration list` and `migration repair` at 2.118.0 and outranks the link file; `db query`
accepts it too, but whether it outranks the link file there was not tested (on 2026-10-06 `--linked`, the link
file and the flag all named TEST — read the link file back before each `db query`), and
neither the dry run nor the push prints which project it reaches. A fresh clone is not linked — `--linked`
then fails, or follows a stray `SUPABASE_PROJECT_ID`. The human PROD procedure uses the PROD ref the same
way (`docs/database-changes/S0.2-0000-init.md`). Never run `db reset` against a remote project, never
`--include-seed` (seeding is disabled in `config.toml` as well), never a down file through `db push`.

## S1.1 data tools (TEST only — every one a dry run without `--apply`)

```bash
pnpm db:test:seed                                              # the catalogue plan vs TEST: 22 artworks, 66 variants, 330 image rows, 7 policy versions, business_rules v1
pnpm db:test:seed --apply                                      # writes missing rows; a differing row is reported, not overwritten (--overwrite applies the plan, referenced variants kept)
pnpm db:test:upload-catalogue --source-root <checkout of b24dce1b…>          # verifies the pinned checkout and every enumerated WebP by SHA-256
pnpm db:test:upload-catalogue --source-root <checkout of b24dce1b…> --apply  # uploads 330 objects to the public bucket catalogue-public (idempotent)
pnpm db:test:reset --namespace=catalogue:                      # deletes only the seeded catalogue rows, refused while an order references a variant
pnpm db:test:reset                                             # the S0.2 form: synthetic system_checks rows of one namespace (fixture: / integration:)
```

## Recovery

Prefer forward fixes: every planned migration is additive. When a schema rollback is unavoidable, the paired
`rollbacks/*.down.sql` is run by hand after the checks in the change record, on TEST first (for S1.1,
`0002_orders.down.sql` before `0001_catalogue.down.sql` — `order_items` references the catalogue), and the
reversal is then recorded in the ledger with `supabase migration repair --status reverted <version>
--project-ref <REF>`. Who may run a down file and through which channel is stated once, in
`docs/database-changes/S1.1-0001-catalogue.md` → "Rollback rehearsal": on TEST the owner in the SQL editor,
or the builder with `db query --linked --project-ref <TEST_REF> --file …` under the owner's written
authorisation naming the files and the project (on 2026-10-06 both `supabase-dev` calls carrying a down file
came back declined in this client, so the rehearsal was run with the CLI); on PROD the human owner only.
The 0001 down file leaves the `catalogue-public` bucket and its objects in place — Storage refuses a SQL
delete on its tables and one would orphan the files; remove them through the Storage API (the dashboard) if
they must go. Host rollback (Vercel Instant Rollback) never touches the database.
