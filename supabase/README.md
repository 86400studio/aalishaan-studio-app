## Layout

| Path | Purpose |
|---|---|
| `migrations/NNNN_name.sql` | Forward migrations, applied in version order. `0000_init.sql` is the S0.2 baseline; `0001_catalogue.sql` and `0002_orders.sql` are S1.1 (drafted 2026-10-05, corrected, applied to TEST and the rollback rehearsed there on 2026-10-06; applied to PROD by the owner on 2026-10-11 and verified read-only — their records in `docs/database-changes/`); `0003_staff_auth.sql` is S1.2 (drafted 2026-10-12 in the cloud build leg; applied to TEST on 2026-10-13 under the owner's authorisation, verified read-only and the rollback rehearsed there the same day — the rehearsal leaves the three new columns at attribute numbers 10–12 on TEST for good; not yet applied to PROD — the owner's own apply, after the review and before the merge; its record `docs/database-changes/S1.2-0003-staff-auth.md`). The CLI's file pattern is `^([0-9]+)_(.*)\.sql$` (verified in its source at 2.117.0), so the roadmap's four-digit versions are discovered as written; only a 14-digit `<timestamp>_init.sql` older than `20211209000000` would be skipped as a legacy dashboard file. |
| `rollbacks/NNNN_name.down.sql` | The paired schema-recovery artifact of each forward file — **outside `migrations/`**, so `db push` can never run it. A down file reverses schema; it does not restore data and it is never run because it exists. |
| `config.toml` | The CLI's project configuration (generated by `supabase init` 2.117.0; `project_id` set, seeding disabled). Local Docker development is not used in this project. |
| `.gitignore` | The CLI's own: `.branches/`, `.temp/` (where `link` keeps the linked ref). Nothing under `supabase/` holds a value. |

## What the CLI does when it applies a file

Each forward file is sent as **one pipelined batch that ends with the ledger insert** into
`supabase_migrations.schema_migrations (version, name, statements)` — for `0000_init.sql` the version is
`0000` and the name `init`. The extended protocol runs a pipeline as one implicit transaction, so a failing
statement rolls back the file and its ledger row together (statements that cannot run inside a
transaction, such as `CREATE INDEX CONCURRENTLY`, are executed on their own — the baseline has none). The
dashboard SQL editor runs a pasted script as one implicit transaction too, but it writes no ledger row.

## Commands (names only — the CLI prompts for or reads secrets itself; never paste one)

Authentication: `pnpm exec supabase login` once (browser flow; the access token goes to the OS credential
store) or `SUPABASE_ACCESS_TOKEN` in the trusted process. At 2.118.0 `link` neither asks for nor stores a
database password; `migration list`, `db push` and `migration repair` take one only from `--password` or
`SUPABASE_DB_PASSWORD`, and without one they sign in with the access token and create a temporary login role
on the project named on the command ("Initialising login role…"). `db query` has no `--password` flag; on
2026-10-06 `db query --linked --project-ref <TEST_REF>` printed the same "Initialising login role…" and
reached TEST. **The token is account-wide, so the project
ref on each command is the only thing that separates TEST from PROD** (S1.1, 2026-10-06 — the 0001 record).

```bash
pnpm exec supabase --version                                  # 2.118.0
pnpm exec supabase link --project-ref <TEST_REF>              # once per checkout, by the owner in their own terminal; writes supabase/.temp/project-ref
cat supabase/.temp/project-ref                                # read the link back: it must print the TEST ref
pnpm exec supabase migration list --project-ref <TEST_REF>    # local files vs the remote ledger
pnpm exec supabase db push --project-ref <TEST_REF> --dry-run # prints what would be applied; applies nothing
pnpm exec supabase db push --project-ref <TEST_REF> --yes     # TEST apply — only under the owner's explicit authorisation (--yes: the builder's process has no terminal)
pnpm exec supabase db dump --project-ref <TEST_REF> --schema public -f <scratch>/test-schema.sql   # schema capture for P8 (needs Docker; S1.1 uses the catalog query of the 0001 record instead)
pnpm exec supabase db query --linked --project-ref <TEST_REF> --file supabase/rollbacks/<file>     # a down file on TEST — only under the owner's written authorisation naming the file and the project ("Recovery" below)
```

Name the project on every command that reaches a database (S1.1, 2026-10-06): `--project-ref <REF>` is
accepted by `db push`, `migration list` and `migration repair` at 2.118.0 and outranks the link file; `db query`
accepts it too, but whether it outranks the link file there was not tested (on 2026-10-06 `--linked`, the link
file and the flag all named TEST — read the link file back before each `db query`), and
neither the dry run nor the push prints which project it reaches. A fresh clone is not linked — `--linked`
then fails, or follows a stray `SUPABASE_PROJECT_ID`. The human PROD procedure uses the PROD ref the same
way (`docs/database-changes/S0.2-0000-init.md`). Shown on 2026-10-11: from a checkout whose link file named
TEST, `migration list`, `db push --dry-run` and `db push` carrying `--project-ref <PROD_REF>` reached
Production (the owner's apply of 0001 and 0002, verified read-only afterwards — PR #18). Never run `db reset`
against a remote project, never `--include-seed` (seeding is disabled in `config.toml` as well), never a down
file through `db push`, and never `config push`: `config.toml` carries the CLI's local Auth defaults (sign-up
on, TOTP off) — the opposite of the dashboard settings the staff sign-in rests on (`ENVIRONMENT-PARITY.md`
§7.5) — and pushing it would send them to the named project.

## S1.1 data tools (TEST only — every one a dry run without `--apply`)

```bash
pnpm db:test:seed                                              # the catalogue plan vs TEST: 22 artworks, 66 variants, 330 image rows, 7 policy versions, business_rules v1
pnpm db:test:seed --apply                                      # writes missing rows; a differing row is reported, not overwritten (--overwrite applies the plan, referenced variants kept)

pnpm db:test:upload-site-images --source-root <checkout of b24dce1b…>        # S1.3 (D-48): verifies the 20 site images of scripts/testing/site-images.json by SHA-256 and encodes the seven PNG sources to WebP (Chromium), then reads TEST — five identity probes and one listing per image (25 read requests: 23 with the secret key, 2 with the publishable key, both from .env.local); nothing uploaded
pnpm db:test:upload-site-images --source-root <checkout of b24dce1b…> --apply # uploads the missing objects to catalogue-public under site/ (20 on an empty prefix — 45 requests); same keep / --overwrite rule as the catalogue upload

```

## S1.2 staff fixtures (TEST only — a dry run without `--apply`)

```bash
pnpm db:test:staff-users                              # the three fixtures (owner, Operations, Customer support) vs TEST: which users and profiles exist
pnpm db:test:staff-users --apply                      # creates the missing Auth users (admin API, confirmed, no mail) from E2E_STAFF_<ROLE>_EMAIL / _PASSWORD and inserts their staff_profiles rows; a differing row is reported, never overwritten
pnpm db:test:staff-users --apply --reset-mfa          # removes every MFA factor of the three fixtures so the Playwright auth-setup project enrols again (keep .auth/ — the setup replaces the kept keys itself)
pnpm db:test:staff-users --apply --revoke operations  # the S1.2 revocation exercise: active = false, revoked_at, an Auth ban, an audit row — the next request is denied
pnpm db:test:staff-users --apply --restore operations # the reverse, with its audit row (the owner fixture is never revoked by the tool)
```

Addresses must end in `@example.test`; nothing is written without `--apply`; PROD is refused before any request; no password or secret is ever printed. The guard reads `staff_profiles.active` on every request, so `--revoke` is visible on the next `/admin` request of that fixture. **On TEST since 2026-10-13:** the three fixtures exist — created by `pnpm db:test:staff-users --apply` ("Users: 3 created. Profiles: 3 inserted; the rest kept."), each enrolled through the real pages on the Preview by the Playwright auth-setup project — and they stay: no tool or grant in the repository removes an Auth user or a staff row. The six `E2E_STAFF_*` values are fixed from that first apply — a changed address would create a fourth user and staff row, a changed password is ignored — and the harness's `.auth/` folder must be kept: a fixture with a verified factor and no kept key can only be reset. Seen or read on TEST in the exercises of that day (`docs/sprint-prompts/S1.2-staff-auth.md` → "TEST run — steps 2 to 8 and 10" and "The recovery exercise — step 9"): the revoked fixture's next request met "Access revoked" — whether the Auth server's refusal of the banned member's token or the inactive row answered cannot be told from the page; `--restore` made the fixture's unexpired session usable again; neither `--reset-mfa` nor the removal of a factor in the dashboard ended a session — the Auth server kept the sessions and set them to aal1 (read, both times), the app sent such a session to the enrolment page (seen after `--reset-mfa`), and the sessions were gone once a new factor was verified (read) — so a recovery after a suspected compromise ends the sessions first (S2.1's procedure; `docs/THREAT-MODEL.md` §5).

## Recovery

Prefer forward fixes: every planned migration is additive. When a schema rollback is unavoidable, the paired
`rollbacks/*.down.sql` is run by hand after the checks in the change record, on TEST first, newest file
first: from S1.2 on `0003_staff_auth.down.sql`, then `0002_orders.down.sql`, then `0001_catalogue.down.sql`
(0003's function depends on the `staff_role` type that 0002's down file drops; `order_items` references the
catalogue), and the
reversal is then recorded in the ledger with `supabase migration repair --status reverted <version>
--project-ref <REF>`. Who may run a down file and through which channel is stated once, in
`docs/database-changes/S1.1-0001-catalogue.md` → "Rollback rehearsal": on TEST the owner in the SQL editor,
or the builder with `db query --linked --project-ref <TEST_REF> --file …` under the owner's written
authorisation naming the files and the project (on 2026-10-06 both `supabase-dev` calls carrying a down file
came back declined in this client, so the rehearsal was run with the CLI); on PROD the human owner only.
The 0001 down file leaves the `catalogue-public` bucket and its objects in place — Storage refuses a SQL
delete on its tables and one would orphan the files; remove them through the Storage API (the dashboard) if
they must go. Host rollback (Vercel Instant Rollback) never touches the database.
